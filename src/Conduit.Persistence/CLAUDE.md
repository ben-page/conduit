# Conduit.Persistence

Shared relational-persistence abstraction used by Conduit's storage modules (Durability and Audit). Engine-agnostic — targets `net10.0`, references Conduit core + the DI/Hosting abstractions. The concrete engine lives in a separate package (e.g. `Conduit.Persistence.Sqlite`) and is registered into core's `ConduitBuilder` via a `UseXxx` extension, mirroring how transport packages register via `UseTransport`.

## Abstraction surface

- **`IConduitConnectionFactory`** — `Task<DbConnection> CreateConnectionAsync(CancellationToken)` opens a fresh connection that the **caller owns and disposes**. `DbTransaction? GetCurrentTransaction()` has a default `null` implementation (audit never overrides it; durability's transaction-aware factories do, to surface the handler's ambient transaction for the outbox write path). The four engine factories dispose a connection whose `OpenAsync` throws, then rethrow (the caller never received it; `await connection.OpenAsync(...); return connection;` leaked it): `ConnectionFactoryShould.DisposeOnOpenFailure` (Durability tests) proves it on SQLite through the internal `SqliteConduitConnectionFactory(Func<SqliteConnection>)` seam (`InternalsVisibleTo Conduit.Durability.Tests`); the other three share the pattern.
- **`INonTransactionalConnectionFactory`** — public marker. Built-in connection-string factories implement it; they can never enlist the handler's transaction. The durability outbox does an `is INonTransactionalConnectionFactory` fail-fast at startup. Public so consuming modules can run that check. (Marker interface; uses the same `#pragma warning disable CA1040` convention as core's `IEvent`.)
- **`ISqlDialect`** — one implementation per engine, exposing every idiom both modules use:
  - `DbType TimestampDbType` and `DbParameterHelper` for binding.
  - DDL type-name helpers (`BigIntAutoIncrementPrimaryKey`, `TimestampType`/`NullableTimestampType`, `TextType`/`NullableTextType`, `KeyTextType`, `BlobType`/`NullableBlobType`, `IntegerType`, `SmallIntType`). Modules compose their own CREATE TABLE strings from these — **DDL templates stay in the module**, only the engine type vocabulary lives here. `KeyTextType` is the bounded text type (`NVARCHAR(450)` on SQL Server, `VARCHAR(255)` on MySQL, `TEXT` elsewhere) for any column a key or an index covers, an indexed timestamp included: SQL Server's and MySQL's general text and timestamp types are unbounded and cannot be index keys.
  - `BuildCreateTableIfNotExistsSql(table, columns)` (one statement) and its overload `BuildCreateTableIfNotExistsSql(table, columns, IReadOnlyList<TableIndex> indexes)` (the statements to run in order; `TableIndex(Name, Columns)` is a record in this package). SQLite/Postgres follow the table with `CREATE INDEX IF NOT EXISTS`, SQL Server guards each `CREATE INDEX` with a `sys.indexes` check, so all three add a missing index to an existing table; MySQL has no `CREATE INDEX IF NOT EXISTS` and no guard outside a stored program (a prepared statement built in a user variable is refused by MySqlConnector unless `AllowUserVariables`), so it declares the indexes inside its one `CREATE TABLE IF NOT EXISTS` and an existing table is left alone. Postgres names indexes per schema, so index names must be unique beyond their table. Each SQL Server create (table or index) is one batch: `SET XACT_ABORT ON; SET TRANSACTION ISOLATION LEVEL READ COMMITTED; BEGIN TRANSACTION; DECLARE @lock int; EXEC @lock = sp_getapplock @Resource = N'conduit_create_if_absent', @LockMode = N'Exclusive', @LockOwner = N'Transaction'; IF @lock < 0 THROW 51000, N'Conduit could not take its create lock.', 1;` then the guarded create, then `COMMIT TRANSACTION;`. `XACT_ABORT` rolls the transaction back when the client times out or cancels (otherwise it stays open on the pooled connection, holding the lock), and a lock not granted ends the batch with an error rather than creating without it. The application lock (database-scoped, released at commit or by the pool's reset) makes replicas create one at a time: measured on SQL Server 2022, eight replicas racing without it deadlocked (1205) in 3 of 8 runs, two `CREATE INDEX` on one table each holding the table's shared lock and waiting for the schema-modification lock. READ COMMITTED because a session carrying Snapshot fails DDL that meets another session's DDL on the same table with 3961 (seen in `SqlServerCarriedIsolationEngineShould.TolerateAConcurrentCreate`). The batch is not parameterized, so its SET stays on the pooled session (READ COMMITTED, the default). Pinned by the four `*DialectShould` tests and `PersistenceEngineTestBase.CreateTheOutboxIndexes`.
  - `IsAlreadyExists(DbException)` — whether the exception is the engine's refusal of a create because the table or index exists, the error the loser of two replicas' create-if-absent gets: SQL Server 2714 (table) / 1913 (index); Postgres 42P07 (`duplicate_table`, tables and indexes) / 42710 (`duplicate_object`, a table's row type) / 23505 with `SchemaName` `pg_catalog` (`pg_class_relname_nsp_index`, `pg_type_typname_nsp_index`; a unique violation in an application table is a data error and stays `false`); MySQL 1050 / 1061 (`MySqlErrorCode.TableExists` / `DuplicateKeyName`); SQLite never (one writer at a time: `IF NOT EXISTS` is atomic). `DbStoreBase.EnsureCreatedAsync` uses it. Pinned by `PersistenceEngineTestBase.RecognizeItsAlreadyExistsErrors` (each engine's real error for a second `CREATE TABLE`/`CREATE INDEX`, and `false` for a duplicate row) and `SqliteDialectShould.TakeNoErrorForAConcurrentCreate`.
  - `BuildReadCommittedSql(statement)` — the statement pinned to READ COMMITTED whatever level the session carries: SQL Server prefixes `SET TRANSACTION ISOLATION LEVEL READ COMMITTED;` (at a carried Snapshot the second of two updates of one row fails with 3960 instead of waiting and re-checking its `WHERE`), the other three return it as it is (Npgsql and MySqlConnector reset a pooled session; SQLite has no level). For a module-owned update callers race on one row; the dead-letter replay claim and its release use it (`ClaimADeadLetterForOneReplayUnderConcurrency` failed with 3960 on the carried-Snapshot class without it).
  - `BuildInsertOrIgnoreSql(table, columns, primaryKeyColumn)` — insert-or-ignore (SQLite: `INSERT OR IGNORE`; Postgres: `ON CONFLICT (...) DO NOTHING`; SQL Server: `INSERT ... SELECT ... WHERE NOT EXISTS`; MySQL: `INSERT IGNORE`).
  - `PaginationSuffix` — ordered-SELECT page clause (SQLite/Postgres/MySQL: `LIMIT @PageSize OFFSET @Offset`; SQL Server: `OFFSET @Offset ROWS FETCH NEXT @PageSize ROWS ONLY`).
  - `BuildExistsSql(table, whereColumn)` — single-row existence probe. SQLite/Postgres/MySQL cap with `LIMIT 1`; SQL Server omits the cap (no `LIMIT` syntax). Routed through the dialect because the inbox `Exists` query is engine-divergent.
  - `BuildClaimPendingSql(IClaimableTableSchema)` / `BuildClaimByIdsSql(IClaimableTableSchema)` — the **complete** atomic outbox-claim SQL with identifiers substituted from the schema. The claim logic (claim token, pending→claiming transition, stale-claim grace cutoff, stuck-row recovery, and the next-attempt cutoff `NextAttemptAtColumn <= @Now` that makes a failed row wait out its backoff) is preserved per-engine; only table/column identifiers are templated. **Status literals are bound parameters** (`@PendingStatus`/`@ClaimingStatus`) — the dialect carries no module-specific status knowledge; the durability outbox store supplies the actual `OutboxEntryStatus` enum values. Each engine uses its own concurrency primitive: SQLite none (single-writer), Postgres/MySQL `FOR UPDATE SKIP LOCKED` (MySQL wraps the row-selection in a derived table since it cannot reference the UPDATE target in a subquery), SQL Server `TOP (@BatchSize)` + `WITH (ROWLOCK, UPDLOCK, READPAST)`, with the batch opening `SET TRANSACTION ISOLATION LEVEL READ COMMITTED;` — `READPAST` refuses the Snapshot or Serializable level a pooled session may carry (SQL 650; measured on SQL Server 2022 with SqlClient 7.1.1, `SqlServerPooledSessionShould`). The session reads its carried level after a claim (`SqlServerClaimIsolationShould`); the likely reason is that SqlClient sends a parameterized command through `sp_executesql`, where a SET reverts on return.
- **`IClaimableTableSchema`** — table + column accessors the claim builders need (`TableName`, `IdColumn`, `MessageIdColumn`, `StatusColumn`, `CreatedAtColumn`, `NextAttemptAtColumn`, `ClaimedAtColumn`, `ClaimTokenColumn`, `AttemptCountColumn`). The pending claim compares `CreatedAtColumn` against `@GraceCutoff` and `NextAttemptAtColumn` against `@Now`: the outbox maps them to `CreatedAt` and `NextAttemptAt`, the jobs ledger maps both to `RunAt` and binds both cutoffs to the same instant.
- **`DbStoreBase`** — abstract base for ADO.NET stores. Provides the disposal-correct connection-per-method pattern (`await using var connection = await ConnectionFactory.CreateConnectionAsync(...)`) with `ExecuteNonQueryAsync` / `ExecuteScalarAsync` / `ExecuteReaderAsync<T>` helpers, plus a static `ExecuteOnConnectionAsync(connection, transaction, ...)` for the outbox `SaveAsync` path that writes through a **caller-supplied transaction's own connection** (which the store does not own). `EnsureCreatedAsync(dialect, statements, ct)` runs create-if-absent statements in order, each on its own connection, and passes over one that fails with `dialect.IsAlreadyExists` (another replica created that table or index between its check and its create), so the statements after it still run: every store's `EnsureTableExistsAsync`/`EnsureTablesExistAsync` (outbox, inbox, DLQ, audit, jobs) goes through it. Per statement, not "catch at the initializer and re-run the ensure once": measured on PostgreSQL, the loser's error arrives as the winner commits, so the re-run races the winner's next statement and fails again (it did, with 23505 on `pg_type_typname_nsp_index`, and on SQL Server with 1913). CA2100 is suppressed at the class level by `[SuppressMessage]` with justification (all SQL is trusted infrastructure) — the same attribute-based approach the stores used before extraction.
- **`DbParameterHelper`** — static `Add(command, name, value)` and `Add(command, name, value, DbType)`.
- **`TableInitializerBase : IHostedService`** — scoped-on-startup table creation. Overridable `ValidateConfiguration(IServiceProvider scope)` hook (fail-fast) and `CreateTablesAsync(IServiceProvider scope, ...)`. Replicas starting together on an empty database all start: the stores' `EnsureCreatedAsync` tolerates a concurrent create, and SQL Server's creates serialize on their application lock. `PersistenceEngineTestBase.TolerateAConcurrentCreate` races eight initializers that each create every store's tables (`EveryStoreTableInitializer`) on one fresh database per server engine, and asserts every outbox index; `TableInitializerShould.TolerateAConcurrentCreate` (Durability tests) does the same on a SQLite file. Before the fix it failed on PostgreSQL (23505 on `pg_class_relname_nsp_index`) and SQL Server (1913); MySQL passed, its metadata lock serializing the creates.
- **`PeriodicCleanupServiceBase : BackgroundService`** — `abstract Interval` + `abstract CleanupAsync(IServiceProvider scope, ...)`; each tick runs in a fresh `IServiceScopeFactory` scope so a scoped store can be resolved safely. A tick that throws is logged and the next runs after `Interval` (while the host is stopping, any exception is the stop's cancellation and logs nothing — SqlClient reports one as a `SqlException`) — escaping, it ended the service and, under the default `StopHost`, the host. It logs under the derived type's category through `ILoggerFactory` resolved from the first tick's scope, so derived constructors take no logger.

## Engine-package pattern

An engine package references `Conduit.Persistence` + its ADO.NET provider and ships:
1. A `IConduitConnectionFactory` (+ `INonTransactionalConnectionFactory`) backed by a connection string, which disposes a connection that fails to open before rethrowing.
2. An `ISqlDialect` implementation.
3. A `public static ConduitBuilder UseXxx(this ConduitBuilder builder, string connectionString)` extension that registers `IConduitConnectionFactory` (Scoped) + `ISqlDialect` (Singleton) into `builder.Services`. `ConduitBuilder.Services` is already public (same access transport extensions use), so no new accessor is needed.

Consuming modules resolve `IConduitConnectionFactory` + `ISqlDialect` from DI and never reference a specific engine. See `Conduit.Persistence.Sqlite` for the reference implementation.

## Engine packages

Four engine packages ship today, all implementing the **complete** `ISqlDialect` surface above:

| Package | Connection factory | Dialect | Extension | Provider |
|---|---|---|---|---|
| `Conduit.Persistence.Sqlite` | `SqliteConduitConnectionFactory` | `SqliteDialect` | `UseSqlite` | Microsoft.Data.Sqlite |
| `Conduit.Persistence.Postgres` | `PostgresConduitConnectionFactory` | `PostgresDialect` | `UsePostgres` | Npgsql |
| `Conduit.Persistence.SqlServer` | `SqlServerConduitConnectionFactory` | `SqlServerDialect` | `UseSqlServer` | Microsoft.Data.SqlClient |
| `Conduit.Persistence.MySql` | `MySqlConduitConnectionFactory` | `MySqlDialect` | `UseMySql` | MySqlConnector |

**Column-naming consistency:** all four dialects compose DDL using the consuming module's hard-coded **PascalCase** identifiers (the module's non-claim SQL constants reference `MessageId`, `Status`, `CreatedAt`, etc., and `OutboxTableSchema` exposes the same). PostgreSQL folds unquoted identifiers to lower case, so its DDL and the module's unquoted queries resolve to the same columns transparently; SQL Server / MySQL column names are case-insensitive. This keeps the four engines agreeing on the single set of column names the module owns.

Per-engine claim SQL is asserted byte-for-byte (no DB connection) by `PostgresDialectShould` / `SqlServerDialectShould` / `MySqlDialectShould` in the Durability test project. Container-backed integration tests for all three server engines live in `tests/Conduit.Persistence.IntegrationTests/` (real Postgres/SqlServer/MySql via Testcontainers), exercising the stores end-to-end.
