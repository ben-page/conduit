# Conduit.Transport.Kafka

- `KafkaTransport` — extends `BrokerTransportBase<KafkaInboundMessage>`. Uses `Confluent.Kafka`. Inbound dispatch, lifecycle, and outbound serialization handled by base class. Implements Kafka-specific primitives: producer/consumer management, consumer group routing, dead-letter topic publishing.
- `UseKafka(bootstrapServers, configure?)` registers: singleton transport, `IHostedService` forwarding, non-keyed `IConduitTransport` (for event broadcast), keyed `IConduitTransport` (for endpoint routing), and calls `UseTransport<KafkaTransport>()`
- Default consumer groups per app: shared for commands/queries (unicast), per-app for events (multicast). Both subscribe to the same shared topic; client-side filtering by message type (the `conduit-type` header). The default groups own the **complement** of all pool-claimed types — types not assigned to any pool. Non-owned messages are skipped but their offset is still committed (so the owning group, and only it, processes them).
- Reply topic per app with per-instance consumer group and manual partition assignment
- **Concurrency = N consumer instances per consumer group.** `BuildConsumerGroupSpecs` produces one spec per group; `StartConsumersAsync` starts `InstanceCount` `IConsumer` instances in the same `group.id`. Kafka natively balances the shared topic's partitions across the instances and commits offsets per instance — real parallelism with per-partition ordering, no manual offset tracking. `DefaultConcurrency` drives the default groups' instance count; `pool.Concurrency` drives each pool group's. Instance count is clamped to `KafkaTopologyManager.SharedTopicPartitions` (6): more instances than partitions sit idle (inherent Kafka behavior — each partition is assigned to exactly one consumer in a group). **Effective parallelism is bounded by the shared topic's partition count.**
- **Pools = dedicated consumer groups.** Each pool gets its own deterministic, topology-mode-aware `group.id` (`pool-{name}` suffix on the shared/unicast id for its command/query types, on the per-app/multicast id for its event types). A pool group subscribes to the same shared topic and processes **only** the message types in `pool.MessageTypes`, skipping+committing everything else. Net result: each message is processed exactly once, by the single group that owns its type. Pools are isolated — a slow/blocking pool handler cannot stall the default group or another pool, because each is an independent consumer group with its own instances. Same model as the other broker transports (which use dedicated queues); Kafka uses dedicated consumer groups instead.
- **Outbound partition key** is a per-message id (`MessageContext.Current.MessageId`, fallback fresh GUID), not the type name — so same-type messages distribute across partitions and a group with concurrency > 1 can process them in parallel. The type discriminator travels in the `conduit-type` header, so partition routing is independent of type. There is no cross-message ordering contract between distinct dispatches, so distributing the key is safe.
- Wire format: `conduit-type`, `conduit-message-id`, `conduit-causation-id`, `conduit-conversation-id`, `conduit-reply-topic`, `conduit-correlation-id` headers (UTF-8 byte arrays). Message key = FullTypeName.
- `AbandonAsync` commits offset and publishes to dead-letter topic immediately (no in-process retry — Kafka offsets are sequential, not committing blocks all subsequent messages)
- Topology modes: Production = default retention, Developer = 4h retention, Test = 5min retention (via `retention.ms`).
- `KafkaTopologyReaper.ReapByPrefixAsync(bootstrapServers, prefix)` — public best-effort cleanup that deletes topics + consumer groups whose names start with `prefix`. Used by the test harness (once per project, against the project's `test-{hash}-` prefix) and available to apps. Replaces the removed no-op `CleanupLoopAsync` timer.
- Concurrency: options inherit `BrokerTransportOptions` (core). `DefaultConcurrency` (default groups) and `ReceiverPoolOptions.Concurrency` (pool groups) set the number of consumer instances per group (the N-instances-per-group model above), clamped to the shared topic partition count. Pools are fully implemented as dedicated consumer groups with exactly-once-per-type-group routing.
- Type discovery via `ConduitTypeRegistry` (source-generated, compile-time verified) — no runtime DI scanning
