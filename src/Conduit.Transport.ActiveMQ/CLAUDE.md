# Conduit.Transport.ActiveMQ

User guide: [`docs/transports/activemq.md`](../../docs/transports/activemq.md) — setup, options, configuration keys, topology, pools, wire format, connection recovery, failed messages. Keep user-facing facts there, not here.

- `ActiveMQTransport` — extends `BrokerTransportBase<ActiveMQInboundMessage>`. Uses `AmqpNetLite` (AMQP 1.0). Inbound dispatch, lifecycle, and outbound serialization handled by base class. Implements Artemis-specific primitives: the connection lifecycle and reconnection, two-address publishing, the exclusive reply queue (its receiver hands each reply to the base class's `CompleteReply`), receiver link management.
- `ActiveMQConnection` (internal) — one AMQP connection and everything on it: `Session`, `CommandSender`/`EventSender`, the dynamic reply receiver and its broker-assigned `ReplyAddress` (volatile, set last, so `IsReady` never sees a half-attached connection), the consumer links, and its `ActiveMQReplySenders`. `OpenAsync` passes a 30 s timeout linked with the caller's token to `ConnectionFactory.CreateAsync(address, token)` and backs it with `WaitAsync` (the token does not reach AMQPNetLite's SASL exchange); a connection that opens after the wait gave up is closed. It watches (`AddClosedCallback`) the connection, the session, both senders, the reply receiver and every consumer link, and calls the transport's `onLost` once, the first time one closes while its `closing` flag is unset; `DisposeAsync`, `Abort` and `CloseConsumerLinks` set the flag first, so a close of its own is never a loss. Reply senders are not watched (one closes whenever its requester goes away). `DisposeAsync` closes only the connection (5 s), which ends the session and every link.
- **Reconnection** (in the transport): AMQPNetLite never reconnects. `stateLock` guards `current`, `started`, `stopRequested` and `reconnecting`. `OnConnectionLost` ignores a connection that is not `current` (one already replaced, or one a reconnection is still building, whose attempt then fails); for `current` it reports the loss (`ReportConnectionLost`: logs `ConnectionLost` (Error, EventId 110) with the error the connection recorded with its loss, and calls `FailPendingReplies`, since the dynamic reply queue went with the connection and a waiter could only time out; `TryClaimLossReport` makes it once per connection, because `MarkStarted` may take a connection lost during the start over, nulling `current`, before its close's callback runs, and then reports it itself), and, once `started` and not `stopRequested`, sets `current = null` (so `IsStarted` is false and a send throws) and starts `ReconnectAsync` on the thread pool. `ReconnectAsync` disposes the lost connection, then retries with 1/2/4/8/16/30 s delays (`ReconnectFailed`, Warning, EventId 112): `RebuildAsync` opens a connection, re-runs the topology (`EnsureInboundTopologyAsync` with the type lists `EnsureTopologyAsync` stored, or `EnsureProducerTopologyAsync`) and attaches the senders and a new reply receiver, with `stopToken.Register(Abort)` so stop fails a half-built connection at once; `TryInstall` then, under the lock, refuses if `stopRequested` (the attempt disposes it), throws if the new connection is already lost (retry), else sets `current` before starting the consumers (so a handler's reply finds it) and resets it if they throw. Success logs `Reconnected` (Information, EventId 111) and completes `NextReconnection`. `MarkStarted` (end of `StartConsumersAsync`, or of `EnsureOutboundTopologyAsync` on a producer-only host) starts a reconnection for a connection lost before the start finished. Stop wins: `StopReceivingAsync` sets `stopRequested` under the lock, then cancels `stopCancellation` (the delay, the connect, the registration's `Abort`); `DisposeAsync` does the same, awaits the loop (it never throws) and disposes `current`. `SendReplyAsync` uses `current`, not the connection the request arrived on (a dead connection could not send it); a reply after a reconnection may duplicate one the redelivered request produces, which the requester's correlator ignores. Test hooks: `internal Task NextReconnection`, `internal bool IsConnected` (`ActiveMQReconnectShould`: `ResumeAfterBrokerRestart`, `FailARequestAwaitingItsReplyWhenTheConnectionIsLost`, `StopWhileReconnecting`; `ActiveMQTestBase.StopBrokerAsync`/`StartBrokerAsync`/`RestartBrokerAsync`).
- `ActiveMQReplySenders` (internal, per connection) — one `SenderLink` per reply address, at most `Capacity` (64): `ReplyTo` is the requester's to choose, so the cap is hard. A failed reply is never retried (`BrokerTransportBase.DispatchRequestAsync` logs `ReplyError` and acknowledges the request), so no link may be closed under a send: `SendReplyAsync` holds a `Lease` (`Acquire`, `Release` in a `finally`, `Discard` after a failed send). Each `CachedSender` has an in-flight count and a state (`Open`, `Claiming`, `Evicting`): `TryAcquire` increments then reads the state, `TryClaimIdle` sets `Claiming` then reads the count, both through full fences, so an eviction never claims a link a send holds (and a send never takes a claimed one). `Acquire` leases a cached link lock-free; otherwise, under a `Lock`, it claims links idle for 5 minutes and then the least recently used idle ones (`Recency`, a use counter) until there is room, and if every cached link is held it attaches an uncached link for this reply alone, closed on `Release`. Evicted links are closed after the lock is released, without awaiting (`CloseQuietlyAsync`, 10 s each, concurrently), so a slow detach holds no other reply; plain sender links attaching while others detach is what per-reply links always did. A discarded link leaves the cache at once and closes when its count drains. A link the broker closed is dropped on the next lease. A requester that went away leaves its link attached (probed: Artemis keeps a sender link to a deleted temporary address attached, and a send on it succeeds, auto-creating the address), hence the idle sweep. Nothing to dispose (no semaphore). Tests: `ActiveMQReplySendersShould.CapTheCachedSendersAndEvictTheLeastRecentlyUsed`, `.NeverEvictALinkWithASendInFlight`, `.SendThroughALinkOfItsOwnWhenEveryCachedLinkIsBusy`, `.CloseADiscardedLinkOnlyOnceItsSendsDrain` (internal `Count`, `Lease.IsCached`).
- `UseActiveMQ(connectionString?, configure?)` registers everything **keyed by endpoint name** — options, `ActiveMQTransport` (via `ActivatorUtilities.CreateInstance`, resolving the keyed options), a forwarding non-keyed `IConduitTransport` entry and a forwarding non-keyed `IHostedService` entry (each resolving the endpoint's keyed transport instance) — and calls `UseTransport<ActiveMQTransport>(options)`, which refuses a `ResponseTimeout` that is not positive and finite. No non-keyed `ActiveMQTransport`/options registration exists.
- **Artemis only**, not ActiveMQ "Classic": topology is created through the Artemis management address (`activemq.management`), which Classic does not expose. Management operations take positional JSON-array parameters, and Artemis picks the overload by their count. Every management step is bounded so a reconnection attempt against a broker that accepts a connection and then answers nothing fails instead of hanging (an unbounded one once held a host's disposal past the test timeout): the send at 10 s (`SendAsync(request, ManagementTimeout)`, AMQPNetLite's own timeout, which withdraws the message), the answer at 10 s and the caller's token, the reply-node attach at 30 s and the token, and each management link's close at 10 s. The close must stay a waited one: a non-blocking `Close(TimeSpan.Zero)` made `ResumeAfterBrokerRestart` lose the first request after a reconnection in six runs of seven (the TestCommand queue showed `messagesAdded` 0 with its consumer attached); not explained, see `CloseManagementLinksAsync`.
- Two addresses, `{systemName}-commands` (ANYCAST) and `{systemName}-events` (MULTICAST). Requests and routed `[FireAndForget]` commands (which arrive through `PublishEventAsync`; it picks the anycast sender for a type not in `ConduitTypeRegistry.EventTypeNames`) go to the anycast address, events to the multicast address. Command/query queues are shared, named per type, and carry `CommandQueueFilter` (`JMSType='{FullTypeName}'`). Event queues are per-app on the multicast address, where Artemis copies every message to every bound queue, so each carries `EventQueueFilter` (`JMSType IN ('a','b')`, quotes doubled, each type once in ordinal order so the read-back comparison below ignores the order the registry and the pools list them in; `TopologyManagerShould.WriteTheSameEventFilterForAnyOrderOfTheSameTypes`): the app queue the subscribed events minus every pool-assigned type, a pool's event queue its types that the app subscribes (one queue and one consumer per pool, created only when that set is non-empty). An existing event queue's filter is read (`filter` attribute, `ReadQueueFilterAsync`) at each start and reconnection and re-set with `updateQueue` only when it differs (JSON `{name, filter-string}`; a partial update leaves other fields alone but clears a filter it does not name), so a release that adds an event type receives it (`ActiveMQEventRoutingShould.DeliverAnEventTypeAddedSinceTheQueueWasCreated`). Probed: `updateQueue` leaves the queue's consumers attached (consumer count unchanged, no detach) and they receive the newly admitted type. Command queues are not updated (the filter is fixed by the name). The broker enforces unicast, so unlike RabbitMQ correctness does not depend on only one app binding a type. Tests: `ActiveMQEventRoutingShould.NotDeliverAnotherAppsEventTypes`, `ActiveMQReceiverPoolShould.DeliverAPooledEventOnce` (both read the queue's `messagesAdded` through `Support/ArtemisManagement`), `ActiveMQCommandRoutingShould.DeliverFireAndForgetCommandToHandler`.
- Queues are created with the 19-parameter `createQueue` (`QueueLifetimeFor`): Production durable, no auto-delete; Developer/Test non-durable, `autoDelete` true, `autoDeleteDelay` 4 h / 5 min, `autoDeleteMessageCount` -1 (deleted however full). Artemis deletes such a queue only after it has had a consumer, and checks every `address-queue-scan-period` (30 s). Addresses (`createAddress` takes only a name and routing types) are not auto-deleted: Artemis reaps only addresses it auto-created, and a management-created address survives a restart (both probed). The queue settings are readable only from the configuration `updateQueue` returns (`ArtemisManagement.QueueConfigurationAsync`, restating the filter): `TopologyManagerShould.SetAutoDeleteDelayForEphemeralQueues` is the one container-backed test in `Unit/` (`ActiveMQTestBase.RequireBroker`).
- Reply queue is a per-connection exclusive temporary queue (a dynamic node), deleted with the connection; a reconnection gets a new one. Reply link credit is 200 (`ReplyCredit`): replies settle on arrival, so it only pipelines them.
- AMQP 1.0 wire mapping (`BuildOutboundApplicationProperties`): `Subject`=FullTypeName, native `MessageId`, native `CorrelationId`=ConversationId; `ApplicationProperties` carry the historical `CausationId` (plus `ReplyTo`/`ReplyCorrelationId` for requests) **alongside** the canonical `conduit-message-id`/`conduit-causation-id`/`conduit-conversation-id`/`conduit-source-app` keys — every header the base class assembles is additionally written under its canonical `ConduitHeaders` name. `conduit-source-app` is read by the [self-published event filter](../Conduit/CLAUDE.md) on the inbound side.
- **Durable messages**: every message the transport sends (request, event or `[FireAndForget]` command, reply, redelivery) is built by `NewMessage`, which sets `Header = new Header { Durable = true }`. AMQP's default with no header is non-durable, which Artemis keeps out of its journal, so a broker restart emptied even durable Production queues. A non-durable queue (Developer/Test, the temporary reply queue) holds a durable message in memory like any other. Management requests (`ActiveMQTopologyManager`) stay non-durable. Tests: `ActiveMQDurabilityShould.KeepAQueuedEventAcrossABrokerRestart` (Production topology under a `TestTopologyPrefix` prefix, restarted container, deletes both addresses forced in a `finally` via `ArtemisManagement.DeleteAddressAsync`; `RequireRestartableBroker` first), `.SendRepliesDurable` (a raw AMQPNetLite requester reads `Header.Durable` on the reply).
- Settlement: `AcknowledgeAsync` = `Accept`; `AbandonAsync` = `Modify(deliveryFailed: true, undeliverableHere: false)`, which Artemis counts, so `max-delivery-attempts` (10 by default) moves the message to the dead-letter address (`DLQ` on a stock broker; `ActiveMqDeadLetterShould.RouteAFailedEventToTheDeadLetterAddressWithoutAConduitDlq`); `RequeueAsync` (a delivery after the drain began) = `Release`, not counted. Settling on a link of a lost connection is a silent no-op in AMQPNetLite (the session sends nothing once ended), and the broker redelivers the message. `OnMessageReceived` starts `ProcessInboundAndObserveAsync` unawaited (the link callback is synchronous); it catches what escapes `ProcessInboundMessageAsync` (whose wrapper rethrows to its caller) and logs Error `InboundMessageFailed` (113), as SQS logs its 110, settling nothing again. It used to be a bare `_ = ProcessInboundMessageAsync(...)`, so a rethrow became an unobserved task exception. No container-free seam (it needs a real `ReceiverLink`); covered by the ActiveMQ suite passing through it on every delivery.
- Link names are `{role}-{guid:N}` (`ActiveMQTopologyManager.LinkName`, `ConsumerLinkName()`): unique per link, independent of the queue name (`TopologyManagerShould.UseUniqueLinkNames`).
- `RedeliverAsync` (DLQ replay) sends by FQQN to `ActiveMQTopologyManager.RedeliveryQueue(type, isCommandOrQuery)`: a command/query's shared (or pool) queue on the anycast address, an event's app (or pool) queue on the multicast address. A message sent by FQQN is still filtered (probed), so the app event queue would drop a pooled or command type (`ActiveMqDeadLetterShould.ReplayAPooledEventToItsPoolQueue`).
- `DefaultConcurrency` / `ReceiverPoolOptions.Concurrency` both map to the receiver link credit (prefetch count).
- Type discovery via `ConduitTypeRegistry` (source-generated, compile-time verified) — no runtime DI scanning.
- All configuration keys bind directly through `ConduitConfigurationBinder.BindTransportOptions` — no exclusions, no hand-mapping (`Username`/`Password` are plain strings).
- Stop: `StopReceivingAsync` stops reconnecting (above) and calls `StopReplenishingConsumerCredit` — `SetCredit(0, CreditMode.Auto)`, keeping the links open so a drained handler can still `Accept` on its link. In auto mode AMQPNetLite sends no flow frame for it (decompiled 2.5.4: the credit delta is negative, so no flow; it only stops restoring credit), so Artemis can still push up to each link's outstanding credit during the drain, and the base class releases each one. `CreditMode.Drain` is not used: it sets the link's local credit to 0 at once and sends `drain`, and a transfer already in flight then fails `OnDelivery`'s credit check (`transfer-limit-exceeded`), which AMQPNetLite turns into a close of the whole connection. `StopConsumersAsync` closes the consumer links concurrently, bounded by the shutdown deadline (`WaitUntilDeadlineAsync`; the broker releases anything unsettled); the reply receiver, senders, session and connection close in `DisposeAsync`.
- Not detected: a half-open connection (no AMQP idle timeout is set; enabling one would also need inbound dispatch off AMQPNetLite's I/O thread, which runs `ProcessInboundMessageAsync` up to its first await).
