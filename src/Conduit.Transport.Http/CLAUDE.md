# Conduit.Transport.Http

- `HttpTransport` — outbound C#→C# request/response via HTTP POST. Two `UseHttp` overloads, both keyed by endpoint name and both calling `UseTransport<HttpTransport>()`: `UseHttp(httpClient, basePath?)` wraps a caller-owned `HttpClient` (never reads `BaseAddress` from configuration — the caller owns the `HttpClient`'s address — but does fall back to the endpoint's configured `BasePath` when `basePath` is not supplied, before the `/api/conduit` default; this overload does not construct or register an `HttpOptions` instance, since it only needs the one `BasePath` key); `UseHttp(configure?)` binds `HttpOptions` from the endpoint's configuration section, registers the bound `HttpOptions` as a keyed singleton (matching the broker transports' pattern — inspectable, not bound and dropped), registers its own named `HttpClient` via `AddHttpClient(endpointName, …)`, and resolves it through `IHttpClientFactory` in the keyed transport factory. Known limitation: the transport is a keyed singleton, so `CreateClient(endpointName)` runs once and the client is held for the process lifetime — `IHttpClientFactory`'s handler rotation (and with it DNS refresh) never kicks in. No worse than the caller-supplied-client overload, but the factory buys nothing as written; a host that needs rotation adds `ConfigurePrimaryHttpMessageHandler` with a bounded `PooledConnectionLifetime` to the same named client.
- **Configuration keys** (`Conduit:Endpoints:{endpointName}`): `UseHttp(configure?)` binds full `HttpOptions` via `builder.Configuration?.Bind(options)` before the `configure` callback runs — `BaseAddress` (required), `BasePath` (default `/api/conduit`). `UseHttp(httpClient, basePath?)` only reads the single `BasePath` key (`builder.Configuration?["BasePath"]`), since `BaseAddress` is meaningless once the caller supplies an `HttpClient`. See [`docs/configuration-reference.md`](../../docs/configuration-reference.md#loading-from-iconfiguration) and [`docs/transports/http.md`](../../docs/transports/http.md#loading-from-configuration).
- `MapConduitEndpoint(basePath = "/api/conduit", trustCallerContext = false)` — inbound HTTP wire dispatch endpoint, maps POST `{basePath}/dispatch` and `{basePath}/publish` inside `endpoints.MapGroup(basePath)` and returns that `RouteGroupBuilder`, so `app.MapConduitEndpoint().RequireAuthorization()` reaches both routes (`HttpEndpointShould.ApplyAConventionChainedOnTheReturnedGroupToBothRoutes`). Both answer through the private `Answer(DispatchResult<object>)`: `/publish` catches the `ConduitException` `HandleWireEventAsync` rethrows for a refused event and answers `DispatchResult<object>.Fail(refusal)`, rendered, as `/dispatch` answers a refusal (`TypeFilterShould.RefuseAnUnlistedEventAndAnswerTheCaller`); any other failure propagates as before.
- **Client properties (`HttpDispatchContext.Start(…, readClientProperties)`)** — required, like the trust flag. Only
  `MapConduitEndpoint`'s `/dispatch` and `/publish` pass true; the REST handlers and `WithConduitDispatchContext()`
  pass false. Each `X-Conduit-Property-<name>` header (`PropertyHeaderPrefix`, matched `OrdinalIgnoreCase`; an empty
  name is skipped) becomes the client property `name`, spelled as it arrived (HTTP/2 lower-cases it), value the
  header's `ToString()` (comma-joined when repeated), seeded into `DispatchContextEnrichment.Apply` exactly as
  `ConduitHub` seeds its `headers` argument, so an enricher's write wins. The TS `HttpTransport` sends its `headers`
  this way. Properties alone mint a context (fresh self-causating ids), as an enricher's do. Pinned by
  `HttpDispatchContextShould.ReadClientPropertiesFromHeaders` / `ReadNoClientPropertiesOnARestEndpointOrAnOptedInMinimalApiRoute`.
- **Caller correlation ids (`HttpDispatchContext.Start(httpContext, enrichers, trustCallerContext, readClientProperties)`)** — the flag is a required parameter so every edge decides. Only `MapConduitEndpoint(trustCallerContext: true)` passes true; the REST handlers and `WithConduitDispatchContext()` pass false. Trusted: the `X-Conduit-*` ids are honored only when message and conversation ids are both present and every supplied id passes `MessageContextIds.IsValid` (an empty causation header is absent and defaults to the message id); one bad id discards the set. Otherwise the caller's ids are ignored and the edge behaves as with no headers: fresh self-causating ids when an enricher contributed properties, else no context (the mediator mints). The answer is never affected. Pinned by `HttpDispatchContextShould` (CR/LF and non-ASCII ids are delivered by running the mapped endpoint's request delegate in process over a `DefaultHttpContext`, since no HTTP/1.1 parser delivers CR/LF). `HttpTransport.SendRequestAsync` sends all three headers only when all three ids pass `IsValid`, and none otherwise: a broker can hand the host any id, and `HttpRequestHeaders.Add` throws `FormatException` on CR/LF (`HttpTransportShould.NotForwardAContextThatIsNotPlainTokens`, over a `RecordingHttpMessageHandler`).
- Wire format: request body = plain serialized message JSON, type in `X-Conduit-Type` header, `MessageContext` in `X-Conduit-Message-Id`/`X-Conduit-Causation-Id`/`X-Conduit-Conversation-Id` headers (read only by a trusting edge, above), client properties in `X-Conduit-Property-<name>` headers (the C# `HttpTransport` sends none). Matches the broker wire format (type in transport-native properties, body is the raw message).
- `ConduitRestHandlers` — typed handler helpers for RESTful endpoint mapping (query→route binding, command→body binding)
- `WithConduitDispatchContext()` — a `Finally` convention that wraps the endpoint's request delegate (`DispatchContextEndpointConventionBuilderExtensions`; not an endpoint filter, because a filtered handler is skipped when the response is already 400, which an OpenIddict error-passthrough callback relies on) that opts a plain minimal-API route into the inbound dispatch context: runs the registered `IDispatchContextEnricher`s over `HttpContext.User` and starts the context via `HttpDispatchContext.Start` (same as the wire endpoint and REST-mapped commands), so an in-process `IMediator` dispatch from the handler carries the server-trusted properties (e.g. user id). It also tags the endpoint with the public `ConduitDispatchContextMetadata` (a wrapped delegate is invisible in endpoint metadata), so a host can assert opt-in over its `EndpointDataSource`; applied to a route group (`app.MapGroup("").WithConduitDispatchContext()`) it opts every route in, nested groups included. Opt-in per route or group; routes without it dispatch unenriched. Client-supplied properties are never read, nor the `X-Conduit-*` correlation ids (`trustCallerContext: false`).
- RESTful extension methods (`MapConduitGet<T>`, `MapConduitPost<T>`, etc.) are source-generated into an `internal` `ConduitRestEndpoints` — conditionally emitted only when `Conduit.Transport.Http` is referenced; internal because a module library that sees the transport emits one too, and two public ones collide in the host (CS0121)
- Maps `DispatchResult` errors to HTTP status codes (wire dispatch endpoint) using `DispatchError.Status` when set, falling back to `ErrorCode.ToHttpStatusCode()` for a server predating it (`Status` is 0 then); `ConduitException` → Problem Details (RESTful endpoints). The edges write a refusal in the reader's language: `MapConduitEndpoint` calls `RefusalRendering.RenderResult` on the dispatch answer, and `ConduitRestHandlers.ToProblem` writes `detail` through `RefusalRendering.RenderMessage`, both from `HttpContext.RequestServices` and `MessageContext.Current`
- **File responses**: a query (or RESTful endpoint) returning `BinaryData` emits a real HTTP file response (`Content-Type` from the media type, `application/octet-stream` when null); returning `ConduitFile` (`BinaryData` + optional `MediaType` + optional `FileName`) also sets `Content-Disposition`. A null query result → 404. Conversion happens in `ToHttpResult`.
- **Multipart uploads**: a command with a single `BinaryData`/`ConduitFile` property accepts `multipart/form-data` (other properties bind from form fields); a JSON POST still binds as before. `Internal/MultipartCommandBinder` parses the form; `Internal/FilePropertyMetadata` validates at startup and rejects commands with more than one file property. **Gotcha:** route-bound (GET/DELETE) commands can't declare file properties — they carry no body, so the multipart path never runs and `FilePropertyMetadata.Validate` is never reached for them.
- **Not implemented (deliberately deferred)**: multiple files per command (`IReadOnlyList<ConduitFile>`), `Stream`-based responses/uploads for large (>50MB) payloads, and `Range`/partial-content requests. The one-file-property limit is enforced at startup until multiple-file support lands.
