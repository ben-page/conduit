# Conduit.Transport.RabbitMQ

- `RabbitMQTransport` — extends `BrokerTransportBase<RabbitMQInboundMessage>`. Inbound dispatch, lifecycle, and outbound serialization handled by base class. Implements RMQ-specific primitives: AMQP channel management, topic exchange publishing, consumer management. Reply correlation is the base class's (`AwaitReplyAsync`/`CompleteReply`); the reply consumer copies `args.Body` before handing it over, because the client reuses the buffer.
- `UseRabbitMQ(connectionString?, configure?)` registers everything **keyed by endpoint name** — options, `RabbitMQTransport` (via `ActivatorUtilities.CreateInstance`, resolving the keyed options), a forwarding non-keyed `IConduitTransport` entry and a forwarding non-keyed `IHostedService` entry (each resolving the endpoint's keyed transport instance) — and calls `UseTransport<RabbitMQTransport>()`. No non-keyed `RabbitMQTransport`/options registration exists: two endpoints on RabbitMQ are two independent transport instances with independent options, never a shared last-write-wins singleton. After binding and the callback it validates: a missing connection string throws `InvalidOperationException`; `RabbitMQOptions.ThrowIfConcurrencyOutOfRange` throws `ArgumentOutOfRangeException` for a `DefaultConcurrency` or pool `Concurrency` outside 1..65535 (`RabbitMqOptionsShould`) — the transport packages validate at registration with plain exceptions, as the connection-string check does; none uses `OptionsValidationException` (Conduit.Durability's `AddOutbox` does).
- Wire format: message body = serialized message (JSON), type in `Type` property, MessageContext in native `MessageId` property + historical `CausationId`/`ConversationId` headers (preserved so existing consumers and `ExtractContext` keep working unchanged). `ToRabbitHeaders` (the transport-local mapper; named apart from the base class's `BuildOutboundHeaders` to avoid a same-name, different-signature collision) additionally writes every header from the base class's assembled dictionary under its canonical `ConduitHeaders` key (`conduit-message-id`, `conduit-causation-id`, `conduit-conversation-id`, `conduit-source-app`), so both the historical and canonical forms are on the wire. `conduit-source-app` carries the publishing application's `ApplicationName` (omitted when unset) and is read by the [self-published event filter](../../docs/transports/index.md#self-published-events) on the inbound side.
- Request/response via an exclusive auto-delete reply queue + `ReplyTo` + `CorrelationId` (used only for reply correlation, not MessageContext). The reply queue is **client-named**, `RabbitMQTopologyManager.ReplyQueueName` = `{system}-{app}-replies-{instanceId}` (`instanceId`: a Guid per transport instance). It was server-named (`QueueDeclare("")`): automatic recovery re-declares a server-named queue under a new name, while `replyQueueName` (every request's `ReplyTo`) kept the old one, so after any connection loss no reply arrived again (`RabbitMqCommandRoutingShould.KeepReplyingAfterConnectionRecovery` restarts the broker container mid-test and waits for both connections' `RecoverySucceededAsync`, through the internal `Connection` property). Known edge: if the broker still holds the old connection when the client recovers (a half-open TCP connection it has not timed out yet), re-declaring the exclusive queue fails `RESOURCE_LOCKED`; the client is not known to retry it, so the reply consumer may stay down until the host restarts (unverified, no test).
- **Channels**: `publishChannel` (outbound requests, events, redeliveries, and the topology declarations) and `replyPublishChannel` (replies, `SendReplyAsync`; not opened on a producer-only host) both have publisher confirms on (`ConfirmingChannel`: `publisherConfirmationsEnabled` + `publisherConfirmationTrackingEnabled`; that constructor leaves the outstanding-confirm rate limiter null, so the immutable options are shared), so `BasicPublishAsync` returns once the broker acked and throws `PublishException` on a nack. Replies used to share the publish channel, so a channel error from an outbound publish (an exchange that no longer exists) also closed the channel replies went out on. `replyConsumerChannel` consumes the reply queue; each inbound consumer has its own channel. Every publish stays `mandatory: false`: an event nobody subscribes to is routed nowhere and still confirmed, and a request with no handler times out (`TimeoutWhenNoHandlerAvailable`).
- **All messages flow through the topic exchange**: commands, queries, and events all publish to the single topic exchange with routing key = FullTypeName. Queue bindings route messages to the correct app queue. Reply messages bypass the exchange (direct to reply queue).
- Topology: idempotent `ExchangeDeclare`/`QueueDeclare`/`QueueBind`, always created on startup. Supports topology modes (Production = durable, Developer/Test = auto-delete). Resource names generated by `TopologyNaming`. No direct exchange — single topic exchange only. Pool-assigned types are excluded from the default app queue bindings to prevent dual delivery. `EnsureTopologyAsync` also declares the system's dead-letter exchange (fanout) and queue, both `RabbitMQTopologyManager.DeadLetterName` = `{system}-dead-letter` (shared, no app name), and every inbound queue (app, shared command/query, pool) through `DeclareInboundQueueAsync` with `x-dead-letter-exchange` naming it. The reply queue and the dead-letter queue have none. Producer-only hosts declare neither. The dead-letter queue is never auto-delete (nothing here consumes it, so auto-delete never fires, except to drop the dead letters when some tool's consumer leaves): durable in Production, non-durable in Developer (one per developer prefix), and in Test mode non-durable with `x-expires` 5 minutes, since each test run's prefix would otherwise leave one behind on a long-lived broker; the auto-delete exchange goes with its last binding.
- **Abandon = dead-letter**: `AbandonAsync` is `BasicNack(requeue: false)`, so the broker routes the message to `{system}-dead-letter` once (`RabbitMqDeadLetterShould.RouteAFailedEventToTheDeadLetterExchangeWithoutAConduitDlq`: one listener run, one message on the queue with `x-first-death-reason: rejected`). It was `requeue: true`, a hot loop for a listener that always fails. With a Conduit dead-letter store the base class captures and acknowledges instead, so the broker DLX only sees what Conduit did not capture: an `EventListenerException`, and a thrown `[FireAndForget]` dispatch, on a host without the store (or whose store write failed). Exception: once `StopReceivingAsync` sets `stopping`, `AbandonAsync` requeues, since the base class also abandons a message delivered while draining (`ReturnToBrokerAsync`), which belongs to another instance, not the dead-letter queue; a handler failing during the drain is therefore requeued too, and dead-lettered by whichever instance fails it next.
- Concurrency: each inbound consumer's channel is created with `consumerDispatchConcurrency` = its concurrency and `BasicQos` prefetch = the same value, so up to that many handlers run at once (`RabbitMqConcurrencyShould.RunHandlersInParallelUpToConcurrency` asserts exactly that many, from `ConcurrencyProbeMark`s in the `SpyLog`). With prefetch alone the client's default dispatch concurrency of 1 ran prefetched deliveries one at a time. The consumer handler copies the delivery (`CopyDelivery`: a new `BasicDeliverEventArgs` over `args.Body.ToArray()`) before anything awaits, because the client reuses the body buffer and the base class reads the body late (dead-letter capture, after the handler). Options inherit `BrokerTransportOptions` (core): `DefaultConcurrency` and `ReceiverPoolOptions.Concurrency` are validated 1..65535 by `UseRabbitMQ`, then cast to `ushort`.
- Type discovery via `ConduitTypeRegistry` (source-generated, compile-time verified) — no runtime DI scanning
- **Configuration keys** (`Conduit:Endpoints:{endpointName}`, bound by `ConduitConfigurationBinder.BindTransportOptions` before the `configure` callback runs): `ConnectionString` (required), `DefaultConcurrency` (default `10`, 1..65535), `ResponseTimeout` (default `00:01:00`), `Pools` (array of `{ Name, Concurrency, MessageTypes[] }` — see `AddPool` merge semantics in `src/Conduit/CLAUDE.md`). See [`docs/configuration-reference.md`](../../docs/configuration-reference.md#loading-from-iconfiguration) and [`docs/transports/rabbitmq.md`](../../docs/transports/rabbitmq.md#loading-from-configuration).
- Stop: `StopReceivingAsync` sets `stopping` and `BasicCancel`s the inbound consumers only (`inboundConsumers`, one channel each — a delivery is acked on its own channel, so the channels stay open for the drain, and so do the reply consumer and the reply publish channel). `StopConsumersAsync` closes the inbound channels (requeuing anything unacked) and the reply consumer channel; `DisposeAsync` closes/disposes whatever is left plus the reply publish channel, the publish channel and the connection.
