# Conduit.Durability

Durable messaging infrastructure — inbox (inbound deduplication), outbox (outbound capture + relay), and dead letter queue (capture/browse/replay of failed inbound messages). Configured via `conduit.AddDurability()` with one shared database for all features. User docs: [outbox](../../docs/outbox.md), [dead letter queue](../../docs/dead-letter-queue.md).

## Persistence engine (Conduit.Persistence)

The relational persistence abstraction lives in **`Conduit.Persistence`** (engine-agnostic) with the concrete engine in a separate package (e.g. **`Conduit.Persistence.Sqlite`**). Durability depends on `Conduit.Persistence` only — it has **no** direct database-driver dependency (the `Microsoft.Data.Sqlite` PackageReference was removed). The engine is resolved from DI: `IConduitConnectionFactory` (connections + ambient transaction) + `ISqlDialect` (engine idioms). See `src/Conduit.Persistence/CLAUDE.md`.

- Register the engine on the **`ConduitBuilder`**, not the durability builder: `conduit.UseSqlite(connectionString)` (from `Conduit.Persistence.Sqlite`) — or `UsePostgres` / `UseSqlServer` / `UseMySql` from the sibling engine packages — alongside `conduit.AddDurability(...)`.
- The stores extend `DbStoreBase`; the table initializer extends `TableInitializerBase`; `InboxCleanup` extends `PeriodicCleanupServiceBase`.

## Configuration

- `AddDurability()` extension on `ConduitBuilder` — nests `AddOutbox()`, `AddInbox()`, and `AddDeadLetterQueue()` for feature-specific options. The persistence engine (`IConduitConnectionFactory` + `ISqlDialect`) is configured separately on the `ConduitBuilder` (e.g. `conduit.UseSqlite(cs)`) and shared by all features via DI. Engine selection is **no longer** on the durability builder — `DurabilityBuilder` exposes only `AddOutbox/AddInbox/AddDeadLetterQueue`.
- **Engine-present guard**: `DurabilityTableInitializer.ValidateConfiguration` fails fast at startup if any durability feature is enabled but no `IConduitConnectionFactory`/`ISqlDialect` is registered (pointing at `conduit.UseSqlite(...)`).
- **SQL ownership**: DDL `CREATE TABLE` strings and the non-claim CRUD statements that are **identical across all four engines** (insert, mark-sent, increment-retry, mark-failed, delete-completed, read-back-by-claim-token, DLQ insert/select/count/delete, inbox delete-expired) live in the durability **stores** as module constants. Everything **engine-divergent** is routed through `ISqlDialect`: DDL composed from the dialect's type-name helpers; claim SQL via `BuildClaimPendingSql`/`BuildClaimByIdsSql`; inbox insert-or-ignore via `BuildInsertOrIgnoreSql`; inbox existence probe via `BuildExistsSql` (SQL Server has no `LIMIT 1`); DLQ pagination via `PaginationSuffix`. Row-locking strategies are an engine concern (SQLite needs none; Postgres/MySQL `FOR UPDATE SKIP LOCKED`; SQL Server `TOP` + `ROWLOCK/UPDLOCK/READPAST`) — all four now live in their engine packages (`Conduit.Persistence.{Sqlite,Postgres,SqlServer,MySql}`).
- **Status parameterization**: the claim builders' Pending/Claiming status values are **bound parameters** (`@PendingStatus`/`@ClaimingStatus`), not literals — the dialect carries no durability-domain knowledge. `DbConnectionOutboxStore` supplies `(int)OutboxEntryStatus.Pending` / `Claiming` when executing the claim SQL.
- **Connection ownership**: every store method that obtains a connection via `IConduitConnectionFactory.CreateConnectionAsync` disposes it (`await using`, via `DbStoreBase`). The factory contract is "the caller owns the connection and must dispose it" — a factory must therefore return a fresh, independently-disposable connection per call (the test `StubConnectionFactory` uses a shared-cache in-memory SQLite db so each call opens a new connection over the same data). `DbConnectionOutboxStore.SaveAsync` is the exception: it writes through the caller-supplied `DbTransaction`'s own connection (via `DbStoreBase.ExecuteOnConnectionAsync`) and does not own it.

## Outbox (transactional outbox for reliable F&F delivery)

- `IOutboundInterceptor` in core — generated mediator consults it before local enqueue AND transport send (not just transport); returns `bool`, declining (`false`) without an ambient transaction
- `OutboxCapture` — scoped `IOutboundInterceptor` + `IOutboxFlusher` that buffers `DispatchEnvelope`s. `FlushAsync` claims entries via `IOutboxStore.ClaimByMessageIdsAsync` (same row-locking as relay) immediately after transaction commit, then applies the same local-then-transport contract as the relay from the in-memory buffer: resolve `ILocalEnvelopeDispatcher` from a fresh DI scope (null-tolerant — no generated mediator means no local step, straight to transport), deliver local listeners first, then dispatch via `TransportDispatcher` (skipped for `[LocalOnly]`). No database read — payloads come from memory. Marks sent on success, increments retry on failure. No-op when nothing captured. Safe to not call — relay picks up entries on its normal schedule.
- `IOutboxFlusher` — user-facing interface with `FlushAsync(CancellationToken)`. Always registered by `AddOutbox()`. Users inject this and call after transaction commit for immediate send. EF Core users can auto-wire via `SaveChangesInterceptor` (documented pattern, not built in).
- `OutboxBehavior<TRequest, TResult>` — pipeline behavior that writes captured messages to outbox store within handler's DB transaction. **Each captured outbound message gets its OWN fresh `MessageId`** (`Guid.NewGuid().ToString("N")`); the triggering message's id becomes the `CausationId` and its `ConversationId` is inherited. (Previously all captured entries were stamped with the triggering message's id, so a handler emitting N messages produced N rows sharing one id — a downstream inbox would dedup all-but-one as duplicates, silently losing messages, and `ClaimByMessageIdsAsync` would return multiple rows per id.) After writing, calls `OutboxCapture.SetWrittenMessages` to provide the MessageId-to-envelope correlation for `FlushAsync`.
- `OutboxRelay` — `BackgroundService` that polls for pending entries and sends via `TransportDispatcher`
- **Mandatory transaction-aware connection factory**: the transactional outbox writes entries through `IConduitConnectionFactory.GetCurrentTransaction()`. The built-in connection-string factory (e.g. `SqliteConduitConnectionFactory`, registered by `conduit.UseSqlite(...)`) always returns `null` — it only opens fresh connections for the relay/store sweeps and has no visibility into the handler's transaction. It is tagged with the **public** marker `INonTransactionalConnectionFactory` (in `Conduit.Persistence`). When `AddOutbox()` is enabled, `DurabilityTableInitializer` (startup hosted service) **fails fast** if the resolved `IConduitConnectionFactory` carries that marker, throwing an actionable `InvalidOperationException` (capture would otherwise silently persist nothing). Users MUST register their own transaction-aware `IConduitConnectionFactory` (backed by their DbContext/connection or an ambient `System.Transactions.Transaction`) after `AddConduit` — see [docs/outbox.md](../../docs/outbox.md) "Providing a transaction". `OutboxBehavior` still treats a per-dispatch `null` transaction as legitimate pass-through (a transaction-aware factory may have no active transaction for a given dispatch).
- **Atomic claim (no double-send)**: claiming is a single atomic UPDATE that transitions rows `Pending (0) → Claiming (3)`, stamping `ClaimedAt` and a per-worker `ClaimToken`, then reads back exactly the rows tagged with that token. This makes a row claimable by exactly one worker, so the relay (`ClaimPendingAsync`) and the immediate-send flush (`ClaimByMessageIdsAsync`) can never both dispatch the same entry. (Previously claiming was a `SELECT`-only statement whose row locks released when the connection's implicit transaction ended — before `MarkSentAsync` ran on a different connection — so both paths could claim and send the same rows; SQLite had no locking at all.) The claim SQL is produced by `ISqlDialect.BuildClaimPendingSql`/`BuildClaimByIdsSql` (SQLite: `UPDATE ... WHERE Id IN (SELECT ... LIMIT)`; Postgres/MySQL add `FOR UPDATE SKIP LOCKED`, SQL Server uses `TOP` + `ROWLOCK/UPDLOCK/READPAST` — each in its engine package). The status values are bound `@PendingStatus`/`@ClaimingStatus` parameters supplied by the store. The read-back is uniform (`SELECT ... WHERE ClaimToken = @ClaimToken`, module-owned). **Stuck-row recovery**: a claim older than `DbConnectionOutboxStore.ClaimTimeout` (5 min) is treated as abandoned (crashed worker) and becomes re-claimable. `IncrementRetryAsync` releases the claim back to `Pending` (`Status=0`, `ClaimToken=NULL`) so failed sends are retried; `MarkSentAsync`→`Sent (1)`, `MarkFailedAsync`→`Failed (2)`. The outbox table carries two extra columns: `ClaimedAt`, `ClaimToken`.
- `IOutboxStore` interface with built-in `DbConnectionOutboxStore` (raw ADO.NET). Includes `ClaimByMessageIdsAsync` for immediate-send entry claiming.

## Inbox (idempotent message processing)

- Application-level message deduplication for all inbound wire messages (commands, queries, events). Prevents duplicate handler execution when brokers redeliver messages. Duplicates are silently discarded — no result caching.
- `InboxInterceptor` — `IInboundInterceptor` gate that dedups on `MessageContext.Current.MessageId` via a **single atomic operation**: it calls `IInboxStore.RecordAsync`, which returns whether the row was newly inserted. Newly inserted → proceed (return true); already present → discard (observe `InboxDuplicate`, return false). No-op when no `MessageContext` (local dispatch). (Previously it did `ExistsAsync` then `RecordAsync` as two statements on two connections — a check-then-act TOCTOU race where two concurrent redeliveries of the same MessageId could both pass `ExistsAsync` before either recorded, running the handler twice. The atomic insert closes that window.)
- `IInboxStore` interface with `ExistsAsync`, `RecordAsync` (returns `Task<bool>` — `true` when the row was newly inserted, the atomic dedup primitive), `DeleteExpiredAsync`, `EnsureTableExistsAsync`. Built-in `DbConnectionInboxStore` (raw ADO.NET) returns rows-affected > 0 from `RecordAsync`; the insert SQL is built once via `ISqlDialect.BuildInsertOrIgnoreSql` (SQLite: `INSERT OR IGNORE`; engine variants in their packages) so rows-affected is 0 on a duplicate. `ExistsAsync` remains for callers/tests but is no longer on the dedup hot path; its probe SQL comes from `ISqlDialect.BuildExistsSql` (SQL Server omits the `LIMIT 1`). Table schema: `MessageId` (PK) + `ProcessedAt`.
- `InboxCleanup` — `BackgroundService` that periodically removes expired entries.
- `InboxOptions` — `RetentionPeriod` (default 30min), `CleanupInterval` (default 5min).
- **Edge case: record-then-crash** — if process crashes after `RecordAsync` but before handler completes, the message is recorded as processed but was never handled. At-most-once semantics. Standard trade-off (MassTransit/Wolverine same behavior). Users needing at-least-once should use broker-native retry without the inbox.
- **Broker-native dedup** — ASB `RequiresDuplicateDetection`, SQS FIFO `MessageDeduplicationId` are viable alternatives. Not abstracted by Conduit — configure via passthrough broker options.

## Dead Letter Queue (capture failed inbound messages, browse, replay)

- `IDeadLetters` — user-facing API: `QueryAsync(DeadLetterFilter)`, `GetAsync(id)`, `ReplayAsync(id)` / `ReplayAsync(ids)` / `ReplayByTypeAsync(type)`, `DiscardAsync(id)` / `DiscardAsync(ids)`. Implemented by `Runtime.DeadLetterQueue.DeadLetters`.
- `IDeadLetterStore` + `DbDeadLetterStore` — database persistence (raw ADO.NET; module-owned SQL with pagination/type-names from `ISqlDialect`). Table `conduit_dead_letters`.
- **Capture**: `BrokerTransportBase` writes failed inbound messages to the store on handler failure (after resilience retries), then acks the broker. If the store write fails, or the DLQ is not registered, the message is abandoned and the broker redelivers. `DeadLetterErrorInterceptor` (`IInboundErrorInterceptor`) drives capture.
- **Replay**: re-publishes via `IConduitTransport.RedeliverAsync` (implemented by every transport) — mints a new `MessageId`, carries `OriginalMessageId`, targets the inbound queue directly. Any handler instance picks it up; the inbox won't reject it (new MessageId).
- **Database-only by design (for now).** Broker-native DLQ stores (wrapping ASB/RabbitMQ/SQS/ActiveMQ native DLQs as the Conduit store) were evaluated and deliberately *not* implemented: non-uniform/fragile browse per broker, best-effort filtering, no reliable counts, racy removal, Kafka incompatible, and it duplicates the DB store unevenly. Not a permanent exclusion — could be added later as an additive per-transport option. The broker's own DLQ still acts as an infrastructure safety net when Conduit's DLQ is not enabled. See [docs/dead-letter-queue.md](../../docs/dead-letter-queue.md).
