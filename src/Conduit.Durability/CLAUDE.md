# Conduit.Durability

Durable messaging infrastructure — inbox (inbound deduplication), outbox (outbound capture + relay), and dead letter queue (capture/browse/replay of failed inbound messages). Configured via `conduit.AddDurability()` with one shared database for all features. User docs: [outbox](../../docs/outbox.md), [dead letter queue](../../docs/dead-letter-queue.md).

## Persistence engine (Conduit.Persistence)

The relational persistence abstraction lives in **`Conduit.Persistence`** (engine-agnostic) with the concrete engine in a separate package (e.g. **`Conduit.Persistence.Sqlite`**). Durability depends on `Conduit.Persistence` only — it has **no** direct database-driver dependency (the `Microsoft.Data.Sqlite` PackageReference was removed). The engine is resolved from DI: `IConduitConnectionFactory` (connections + ambient transaction) + `ISqlDialect` (engine idioms). See `src/Conduit.Persistence/CLAUDE.md`.

- Register the engine on the **`ConduitBuilder`**, not the durability builder: `conduit.UseSqlite(connectionString)` (from `Conduit.Persistence.Sqlite`) — or `UsePostgres` / `UseSqlServer` / `UseMySql` from the sibling engine packages — alongside `conduit.AddDurability(...)`.
- The stores extend `DbStoreBase`; the table initializer extends `TableInitializerBase`; `InboxCleanup` extends `PeriodicCleanupServiceBase`.

## Configuration

- `AddDurability()` extension on `ConduitBuilder` — nests `AddOutbox()`, `AddInbox()`, and `AddDeadLetterQueue()` for feature-specific options. The persistence engine (`IConduitConnectionFactory` + `ISqlDialect`) is configured separately on the `ConduitBuilder` (e.g. `conduit.UseSqlite(cs)`) and shared by all features via DI. Engine selection is **no longer** on the durability builder — `DurabilityBuilder` exposes only `AddOutbox/AddInbox/AddDeadLetterQueue`.
- **Engine-present guard**: `DurabilityTableInitializer.ValidateConfiguration` fails fast at startup if any durability feature is enabled but no `IConduitConnectionFactory`/`ISqlDialect` is registered (pointing at `conduit.UseSqlite(...)`).
- **Initializer first**: `AddDurability` registers `DurabilityTableInitializer` before it runs `configure`, so it precedes `OutboxRelay` and `InboxCleanup`. What guarantees the order is the host, not a readiness signal: `Host.StartAsync` starts hosted services one at a time in registration order and awaits each `StartAsync` (`HostOptions.ServicesStartConcurrently` defaults to `false`), and `TableInitializerBase.StartAsync` returns only after `ValidateConfiguration` and the DDL, so neither background service runs its first pass before the tables exist, and a misconfiguration fails startup before either starts. Both query in their first pass (`PeriodicCleanupServiceBase` ticks at once; the relay sweeps at once), so the old order (initializer after `configure`) logged "no such table" at Error on every cold start. A host that sets `ServicesStartConcurrently = true` gives up the ordering: a first pass may then fail once, logged, and the next one succeeds. `AddJobs` relies on the same order for `JobTableInitializer`. Tests: `DurabilityStartupShould.NotSweepBeforeTheTablesExist` (fresh SQLite file, no Error logged), `DurabilityBuilderShould.RegisterTheTableInitializerBeforeTheRelayAndTheCleanup`.
- **Idempotent registration**: a second `AddOutbox`/`AddInbox`/`AddDeadLetterQueue`, from the same builder or another `AddDurability` call, registers nothing twice. Single services are `TryAdd*`; the enumerable ones (`IOutboundInterceptor`, `IInboundInterceptor`, `IInboundErrorInterceptor` for the inbox and the DLQ) are `TryAddEnumerable` with descriptors that name their implementation type — the forwarders use `ServiceDescriptor.Scoped<TService, TImplementation>(factory)`, whose factory delegate type carries `TImplementation` (a `Func<IServiceProvider, TService>` would be refused as indistinguishable). Hosted services go through `AddHostedService` (already `TryAddEnumerable`), and `AddDurability` adds `OutboxBehavior<,>` to `ConduitOptions.PipelineTypes` only when it is not there. Options accumulate: `DurabilityBuilder.RegisteredOptions<T>` finds the `IOptions<T>` instance an earlier call registered and the later callback configures it (so each call changes only what it sets), then `Validate` runs on the result. The outbox's delivery follows the accumulated `CaptureOnly`, so the last call that sets it wins: the flusher is `Replace`d (the no-op `CaptureOnlyOutboxFlusher`, or the `OutboxCapture` forwarder), capture-only removes an `OutboxRelay` an earlier call added, and a later explicit `false` adds it back. Why: two gates in one scope share its `InboxInterceptor`, and the second found the record the first had just made and discarded every message. Tests: `DurabilityBuilderShould.RegisterOneGateWhenAddInboxIsCalledTwice`, `.RegisterOneOutboundInterceptorWhenAddOutboxIsCalledTwice` (also one flusher, one pending writer, one relay, the pipeline once), `.RegisterOneErrorInterceptorWhenAddDeadLetterQueueIsCalledTwice`, `.ApplyEveryAddOutboxCallsOptionsToOneOutbox`, `.StayCaptureOnlyWhicheverAddOutboxCallAskedForIt`, `.RelayAgainWhenALaterAddOutboxCallTurnsCaptureOnlyOff`.
- **Validated options**: `AddOutbox` and `AddInbox` call `OutboxOptions.Validate()` / `InboxOptions.Validate()`, which collect every failure and throw one `OptionsValidationException` (the type the outbox already used). The duration bounds live in `DurationLimits` (`LongestDuration` one day, `LongestRetention` 3650 days, and the `RequirePositive`/`RequireNotNegative` checks): positive and at most a day for `RelayInterval`, `CleanupInterval`, `ClaimTimeout` and the inbox's `CleanupInterval` (the relay's `RelayInterval` and the inbox's `CleanupInterval` feed `Task.Delay`, where a negative one throws and zero spins; the outbox's `CleanupInterval` is compared once per sweep, where one not positive would clean on every sweep); not negative and at most a day for `GracePeriod` (the claim subtracts it from now); not negative and at most 3650 days for `CompletedRetention`/`FailedRetention` (`TimeSpan.Zero` keeps rows forever; `TimeSpan.MaxValue` threw in the cleanup's subtraction from now every interval); positive and at most 3650 days for the inbox's `RetentionPeriod`; `BatchSize` positive; `MaxRetries` at least 2 (the first attempt counts, so 1 made every failure final). A filter is not options: `DeadLetterFilter.PageSize` and `FailedOutboxFilter.PageSize` must be 1 to their `MaxPageSize` (1000), checked with `ArgumentOutOfRangeException` at the query call, in the user surface (`DeadLetters.QueryAsync`, `OutboxOperations.QueryFailedAsync`) and in the built-in stores (SQL Server refuses a `FETCH` of no rows). `DeadLetters.ReplayByTypeAsync`, which asked for `PageSize = int.MaxValue`, now reads every page at `MaxPageSize`, collecting the ids before it replays any (a replay removes its entry, which would move the later pages), distinct (the DLQ pages newest first, so a capture made meanwhile repeats an entry), stopping on a null token, an empty page or a token equal to the one it asked with (a custom store cannot loop it). Tests: `OutboxOptionsShould.RejectNonPositiveValues` / `.RefuseASingleAttempt` / `.RefuseANegativeGracePeriodOrRetention` / `.RefuseADurationAboveItsCeiling` / `.AcceptZeroToKeepEntriesForever_AndEveryCeilingExactly`, `InboxOptionsShould`, `RefuseAPageSizeOutOfRange` in `OutboxShould`, `DbDeadLetterStoreShould` and `DeadLettersShould`, `DeadLettersShould.ReplayEveryEntryOfATypeAcrossPages` (its `StubDeadLetterStore` pages and refuses a page above the maximum, as the real store does).
- **SQL ownership**: DDL `CREATE TABLE` strings and the non-claim CRUD statements that are **identical across all four engines** (insert, mark-sent, increment-retry, mark-failed, delete-completed, read-back-by-claim-token, DLQ insert/select/count/delete, inbox delete-expired and remove) live in the durability **stores** as module constants. Everything **engine-divergent** is routed through `ISqlDialect`: DDL composed from the dialect's type-name helpers, the outbox's indexes through its `BuildCreateTableIfNotExistsSql(table, columns, indexes)` overload; claim SQL via `BuildClaimPendingSql`/`BuildClaimByIdsSql`; inbox insert-or-ignore via `BuildInsertOrIgnoreSql`; inbox existence probe via `BuildExistsSql` (SQL Server has no `LIMIT 1`); DLQ pagination via `PaginationSuffix`. Row-locking strategies are an engine concern (SQLite needs none; Postgres/MySQL `FOR UPDATE SKIP LOCKED`; SQL Server `TOP` + `ROWLOCK/UPDLOCK/READPAST`, after a batch-level `SET TRANSACTION ISOLATION LEVEL READ COMMITTED` because a pooled session keeps its last transaction's level (measured on SQL Server 2022 with Microsoft.Data.SqlClient 7.1.1, `SqlServerPooledSessionShould`) and `READPAST` refuses Snapshot/Serializable with SQL 650) — all four now live in their engine packages (`Conduit.Persistence.{Sqlite,Postgres,SqlServer,MySql}`).
- **Status parameterization**: the claim builders' Pending/Claiming status values are **bound parameters** (`@PendingStatus`/`@ClaimingStatus`), not literals — the dialect carries no durability-domain knowledge. `DbConnectionOutboxStore` supplies `(int)OutboxEntryStatus.Pending` / `Claiming` when executing the claim SQL.
- **Connection ownership**: every store method that obtains a connection via `IConduitConnectionFactory.CreateConnectionAsync` disposes it (`await using`, via `DbStoreBase`). The factory contract is "the caller owns the connection and must dispose it" — a factory must therefore return a fresh, independently-disposable connection per call (the test `StubConnectionFactory` uses a shared-cache in-memory SQLite db so each call opens a new connection over the same data). `DbConnectionOutboxStore.SaveAsync` is the exception: it writes through the caller-supplied `DbTransaction`'s own connection (via `DbStoreBase.ExecuteOnConnectionAsync`) and does not own it.

## Time

**Nothing in this project reads the ambient clock.** `grep -rn "DateTime.UtcNow\|DateTimeOffset.UtcNow" src/Conduit.Durability/` must return nothing. `AddDurability` registers `TryAddSingleton(TimeProvider.System)` (as `AddJobs` does), and every "now" comes from the injected `TimeProvider`: `DbConnectionOutboxStore` (both claims' grace, claim and next-attempt cutoffs, `SentAt`/`FailedAt`, the backoff's `NextAttemptAt`, a retry's `NextAttemptAt`, both retention cutoffs), `OutboxPendingWriter.WriteUnwrittenAsync` (a new entry's `CreatedAt`, for the writer and `OutboxBehavior`), `OutboxRelay` (the cleanup cadence), `DbConnectionInboxStore` (`ProcessedAt`, the retention cutoff), `DeadLetterErrorInterceptor` (`DeadLetteredAt`) and `DbDeadLetterStore` (a replay claim's time and abandonment cutoff). Each takes it as an optional trailing constructor parameter (null is `TimeProvider.System`), so a store built by hand in a test needs none; DI always supplies the registered one. Waits stay real time (`Task.Delay(RelayInterval)`, the cleanup base's `Interval`), as `DispatchRetryOptions` explains for the core: a faked clock would otherwise never end a wait. So a host that fakes the clock moves cutoffs only by advancing it, and a frozen fake clock holds the outbox's grace period: the relay claims nothing written at that instant (the post-commit flush, which has no grace, still delivers). Tests: `DbConnectionOutboxStoreShould.ClaimByTheInjectedClock` / `.StampAndRetainByTheInjectedClock`, `DbConnectionInboxStoreShould.ExpireARecordByTheInjectedClock`, `OutboxPendingWriterShould.StampEntriesWithTheInjectedClock`, `OutboxRelayShould.CleanUpOnceTheInjectedClockPassesTheCleanupInterval` (`SweepCountingOutboxStore`), `DeadLetterErrorInterceptorShould.StampACaptureWithTheInjectedClock`, `DbDeadLetterStoreShould.TakeOverAReplayClaimOnceItIsAbandoned`, `DurabilityBuilderShould.RegisterTheSystemClockUnlessTheHostHasOne`. The clocks in these tests stand in 2030, so a read of the machine's clock fails them.

**Timestamps are UTC text in one form** (`StoredTimestamp.Format`: `yyyy-MM-ddTHH:mm:ss.fffffffZ`), written and bound alike, because the engines compare them as text. `DbDeadLetterStore` wrote `DeadLetteredAt` and bound `DeadLetterFilter.Since`/`Until` with the caller's offset (`DateTimeOffset.ToString("O")`), so `Since = DateTimeOffset.Now` on a UTC+1 host sorted after earlier `+00:00` values (`DbDeadLetterStoreShould.FilterByInstantRegardlessOfOffset`). The outbox had the same exposure through the public `OutboxEntry.CreatedAt`: a `Local` `DateTime` wrote its offset, so the claim's text comparison saw the entry hours older or younger than it was; a `Local` value is now converted, and `Utc`/`Unspecified` are taken as UTC, as `DbAuditStore` does (`DbConnectionOutboxStoreShould.WriteALocalCreatedAtAsItsUtcInstant`). The inbox had none: every value it writes or binds is its own clock's.

## Outbox (transactional outbox for reliable F&F delivery)

- `IOutboundInterceptor` in core — generated mediator consults it before local enqueue AND transport send (not just transport); returns `bool`, declining (`false`) without an ambient transaction
- `OutboxCapture` — scoped `IOutboundInterceptor` + `IOutboxFlusher` that buffers `DispatchEnvelope`s. `FlushAsync` snapshots the written-message buffer and schedules `ClaimAndDeliverAsync` — an `internal static` routine on `OutboxCapture`, not an instance method — on the singleton `ConduitBackgroundDispatcher`, then returns immediately (`Task.CompletedTask`; no `await` in `FlushAsync` itself). No-op (nothing scheduled) when nothing was captured. The scheduled routine runs under the dispatcher's own stopping token, not the request's, and its closure captures only singletons (`IServiceScopeFactory`, `TransportDispatcher`, `ILogger`) plus the plain-record written-message list — no scoped state, since the request scope (and this `OutboxCapture` instance along with it) is gone by the time it runs. `OutboxCapture` therefore no longer takes an `IOutboxStore` constructor dependency at all: `ClaimAndDeliverAsync` resolves its own from a fresh scope (same row-locking `ClaimByMessageIdsAsync` as the relay; mirrors `OutboxRelay.ProcessPendingAsync`'s scope-per-sweep pattern), then applies the same local-then-transport contract as the relay from the in-memory buffer: resolve `ILocalEnvelopeDispatcher` from a fresh per-entry DI scope (null-tolerant — no generated mediator means no local step, straight to transport), deliver local listeners first, then dispatch via `TransportDispatcher` (skipped for `[LocalOnly]`), passing it that scope's `ILocalEnvelopeDispatcher` so an event is broadcast to every transport (never routed) and a routed `[FireAndForget]` command is sent with no reply awaited, as the relay does. No database read — payloads come from memory. Marks sent on success, increments retry on failure, both under the entry's `ClaimedOutboxEntry.ClaimToken` (see claim-guarded resolution below). Safe to not call — relay picks up entries on its normal schedule.
- `IOutboxFlusher` — user-facing interface with `FlushAsync(CancellationToken)`. Always registered by `AddOutbox()` (the no-op `CaptureOnlyOutboxFlusher` when `CaptureOnly`). Users inject this and call after transaction commit: it schedules immediate post-commit delivery on the background dispatcher and returns — the caller never waits (no read-your-writes guarantee); the relay remains the redelivery backstop. EF Core users can auto-wire via `SaveChangesInterceptor` (documented pattern, not built in).
- `IOutboxPendingWriter` — user-facing, scoped (`OutboxPendingWriter`), registered by `AddOutbox()` in BOTH modes (writing is not delivery; capture-only still writes). `WritePendingAsync(CancellationToken = default)` writes the scope's `OutboxCapture.Unwritten` envelopes through the current transaction and adds them to the written list the flush delivers. For a host's outermost transactional behavior that publishes AFTER its `next()` returns (a downstream application dispatches its domain events there): those publishes are captured, but every `OutboxBehavior` in the scope has already exited, so nothing else writes them — call it after the last publish, before the commit. No-op when nothing is unwritten or no transaction is active. Its write IS `OutboxBehavior`'s: both call `OutboxPendingWriter.WriteUnwrittenAsync` (internal static), so the entry shape and correlation cannot drift.
- `OutboxBehavior<TRequest, TResult>` — pipeline behavior that writes captured messages to outbox store within handler's DB transaction. **Each captured outbound message gets its OWN fresh `MessageId`** (`Guid.NewGuid().ToString("N")`); the triggering message's id becomes the `CausationId` and its `ConversationId` is inherited. (Previously all captured entries were stamped with the triggering message's id, so a handler emitting N messages produced N rows sharing one id — a downstream inbox would dedup all-but-one as duplicates, silently losing messages, and `ClaimByMessageIdsAsync` would return multiple rows per id.) **Each captured envelope is written once per scope**: the behavior runs at the end of EVERY pipeline in the dispatch scope — including the nested pipelines of events a handler publishes inline — so it writes only `OutboxCapture.Unwritten` (the captured envelopes past a written-count prefix), and after a successful `SaveAsync` calls `OutboxCapture.AddWrittenMessages`, which advances that count and APPENDS the MessageId-to-envelope correlation for `FlushAsync` — the flush delivers every row the scope wrote. (Previously every pipeline end re-wrote ALL of `Captured` with fresh MessageIds and `SetWrittenMessages` REPLACED the list: one captured envelope plus two inline-published events gave three rows — the flush delivered one, the relay the other two.) **A faulted pipeline drops the unwritten envelopes it captured**: the behavior notes `Captured.Count` on entry and, if `next()` or its own write throws, calls `OutboxCapture.DiscardUnwrittenCapturedSince(thatCount)` before rethrowing — so a later command in the same DI scope cannot write a failed command's messages into its own transaction. Envelopes captured before the pipeline began (an enclosing handler's, which may catch and carry on) are kept, as are written ones (their rows ride the transaction's commit or rollback); so after a failed `SaveAsync` an enclosing handler's envelopes are still written by a later pipeline. Envelopes captured outside every `OutboxBehavior` (a host behavior publishing after `next()`) are not covered: a host that faults there before `IOutboxPendingWriter.WritePendingAsync` leaves them unwritten in the scope. An envelope whose row a transaction rollback discarded stays marked written — deliberately: the rollback also discarded the state of the handler that captured it (capture and write share the scope's ambient transaction), and a retry that re-runs the handler re-captures fresh envelopes. The one case it loses a message is an app-managed savepoint rolled back after a nested pipeline wrote an envelope captured BEFORE the savepoint.
- `OutboxRelay` — `BackgroundService` that polls for pending entries and sends via `TransportDispatcher`
- **Local delivery is an observed dispatch**: the generated `ILocalEnvelopeDispatcher.PublishLocalEnvelopeAsync` (the flush's and the relay's local step) starts a child of the context the caller restored from the entry (`StartDispatchFromTransport`), emits `DispatchInvoked(type, "Event")` then `DispatchCompleted` / `DispatchFailed`, and restores the caller's context in a `finally`. Each delivery attempt is therefore one audit record: a fresh `MessageId`, `CausationId` = the outbox entry's `MessageId`, the entry's `ConversationId`, kind `Event` (the publish record is lowercase `event`). A failed flush followed by a relay redelivery is two rows. The child is started by `MessageContext.StartLocalDelivery()`, so every attempt's `DeliveredMessageId` is the entry's `MessageId`: a listener's once-per-message work keys on that, as Conduit.Jobs' non-coalescing trigger does (`OutboxEventTriggerShould` pins one run for a failed flush plus a relay redelivery). A listener's nested dispatch is caused by its delivery row. The delivery captures **no payload** (`CaptureAuditPayload` is deliberately absent): the publish row holds the body, and the delivery record must never carry one.
- **Persisted dispatch properties (`OutboxOptions.PersistedProperties`, default empty)**: an `IDictionary<string, Type>` of the `MessageContext.Properties` keys an entry carries, each with its value type — `string`, `int`, `long`, `bool` or `Guid`; `AddOutbox` calls `OutboxOptions.Validate()`, which throws `OptionsValidationException` for any other type or an empty key. `OutboxPendingWriter.WriteUnwrittenAsync` (so `OutboxBehavior` too) writes the current context's listed values as a JSON object into `OutboxEntry.Properties` (column `Properties`, nullable text) through `OutboxProperties.Write` (`Utf8JsonWriter`, no reflection serializer); absent or null values are left out, none present writes NULL, and a value of another type than declared throws `InvalidOperationException`. Both delivery paths restore the bag with `OutboxProperties.Read` and pass it to `MessageContext.StartDispatchFromTransport(…, properties)`: the relay reads the column; the flush gets the same `Read` result on `WrittenOutboxMessage.Properties`, computed from the JSON just written, so a relay retry of a failed flush carries the identical bag (`OutboxDispatchPropertiesShould`). `Read` restores each value as its declared type and drops a key no longer listed or no longer readable as its type; a NULL column gives a null bag (empty `Properties`, as before). The local delivery's child context inherits the bag, so a listener's nested dispatches run under it. **A host that lists no key never touches the column**: `DbConnectionOutboxStore` (optional `IOptions<OutboxOptions>` constructor parameter) adds `Properties` to its INSERT and claimed-entries SELECT only when a key is listed, so a table created before the column existed keeps working; `BuildCreateTableSql` always includes it in a new table, and an existing table's columns are never altered (a host that opts in adds the column itself). `OutboxBehavior` and `OutboxPendingWriter` take the options as an optional trailing constructor parameter (null carries nothing).
- **Mandatory transaction-aware connection factory**: the transactional outbox writes entries through `IConduitConnectionFactory.GetCurrentTransaction()`. The built-in connection-string factory (e.g. `SqliteConduitConnectionFactory`, registered by `conduit.UseSqlite(...)`) always returns `null` — it only opens fresh connections for the relay/store sweeps and has no visibility into the handler's transaction. It is tagged with the **public** marker `INonTransactionalConnectionFactory` (in `Conduit.Persistence`). When `AddOutbox()` is enabled, `DurabilityTableInitializer` (startup hosted service) **fails fast** if the resolved `IConduitConnectionFactory` carries that marker, throwing an actionable `InvalidOperationException` (capture would otherwise silently persist nothing). Users MUST register their own transaction-aware `IConduitConnectionFactory` (backed by their DbContext/connection or an ambient `System.Transactions.Transaction`) after `AddConduit` — see [docs/outbox.md](../../docs/outbox.md) "Providing a transaction". `OutboxBehavior` still treats a per-dispatch `null` transaction as legitimate pass-through (a transaction-aware factory may have no active transaction for a given dispatch).
- **Atomic claim (no double-send)**: claiming is a single atomic UPDATE that transitions rows `Pending (0) → Claiming (3)`, stamping `ClaimedAt` and a per-worker `ClaimToken`, then reads back exactly the rows tagged with that token. This makes a row claimable by exactly one worker, so the relay (`ClaimPendingAsync`) and the post-commit flush (`ClaimByMessageIdsAsync`) can never both dispatch the same entry. (Previously claiming was a `SELECT`-only statement whose row locks released when the connection's implicit transaction ended — before `MarkSentAsync` ran on a different connection — so both paths could claim and send the same rows; SQLite had no locking at all.) The claim SQL is produced by `ISqlDialect.BuildClaimPendingSql`/`BuildClaimByIdsSql` (SQLite: `UPDATE ... WHERE Id IN (SELECT ... LIMIT)`; Postgres/MySQL add `FOR UPDATE SKIP LOCKED`, SQL Server uses `TOP` + `ROWLOCK/UPDLOCK/READPAST` behind its own `SET TRANSACTION ISOLATION LEVEL READ COMMITTED` — each in its engine package). The status values are bound `@PendingStatus`/`@ClaimingStatus` parameters supplied by the store. The read-back is uniform (`SELECT ... WHERE ClaimToken = @ClaimToken`, module-owned). **Stuck-row recovery**: a claim older than `OutboxOptions.ClaimTimeout` (default 5 min; the store reads it from its optional `IOptions<OutboxOptions>`, defaults when absent) is treated as abandoned (crashed worker) and becomes re-claimable, by both claims. `IncrementRetryAsync(id, claimToken, retryDelay)` releases the claim back to `Pending` (`Status=0`, `ClaimToken=NULL`) so failed sends are retried, due again at `NextAttemptAt = now + retryDelay`; `MarkSentAsync(id, claimToken)`→`Sent (1)` with `SentAt`, `MarkFailedAsync(id, claimToken)`→`Failed (2)` with `FailedAt`. The outbox table carries four extra columns: `ClaimedAt`, `ClaimToken`, `NextAttemptAt`, `FailedAt` (plus `Properties`, see persisted dispatch properties above).
- **Indexes and key types**: `DbConnectionOutboxStore.Indexes` creates, through `ISqlDialect.BuildCreateTableIfNotExistsSql(table, columns, indexes)` (`EnsureTableExistsAsync` runs its statements in order): `ix_conduit_outbox_status_next_attempt (Status, NextAttemptAt)` — the pending claim ranges over `NextAttemptAt <= @Now` within `Status = Pending`, and within `Status = Claiming` for the stale-claim branch (`ClaimedAt` a residual, as the grace predicate on `CreatedAt` is in both: `NextAttemptAt` is never before `CreatedAt`), and its `Status` prefix serves the Failed listing/count, the retries by type and the Failed retention delete, Failed rows being few; `ix_conduit_outbox_claim (ClaimToken)` — both claims' read-back; `ix_conduit_outbox_message_id (MessageId)` — the flush's by-id claim; `ix_conduit_outbox_status_sent (Status, SentAt)` — the Sent retention delete over the bulk of the table. No index on `CreatedAt` or `ClaimedAt`: no query seeks on either. Every indexed text column is `KeyTextType` (`MessageId`, `ClaimToken`, and the indexed timestamps `NextAttemptAt` and `SentAt`): `TextType`/`TimestampType` are `NVARCHAR(MAX)`/`LONGTEXT` on SQL Server/MySQL, which cannot be index keys. MySQL gets the indexes only with a new table (the dialect inlines them). Tests: `DbConnectionOutboxStoreShould.CreateTheIndexesItsQueriesUse` (SQLite, columns too), `PersistenceEngineTestBase.CreateTheOutboxIndexes` (all engines, ensured twice).
- **Retention on the outcome**: `DeleteCompletedAsync` deletes `Status = 1 AND SentAt <= cutoff`, `DeleteFailedAsync` `Status = 2 AND FailedAt <= cutoff` (it was `CreatedAt` for both, so an entry sent after a week-long outage was deleted at once). `FailedAt` is the last attempt's failure, set by `MarkFailedAsync` and cleared by both `RetryFailedAsync` overloads; an explicit column rather than a reuse of `ClaimedAt` (which on a Failed row is when its last attempt began), so the column says what the retention counts from. Tests: `DbConnectionOutboxStoreShould.KeepASentEntryForItsRetentionFromWhenItWasSent` / `.KeepAFailedEntryForItsRetentionFromItsLastAttempt` / `.RecordWhenAnEntryFailed_AndForgetItWhenTheEntryIsRetried`, `PersistenceEngineTestBase.DeleteSentAndFailedEntriesByWhenTheyWereResolved` (all engines).
- **Claim-guarded resolution**: the three resolutions are `WHERE Id = @Id AND Status = 3 AND ClaimToken = @ClaimToken` (module-owned, identical on all engines) and return `Task<bool>` (rows affected == 1). Both claims hand out the token: `OutboxEntry.ClaimToken` (set by `ClaimPendingAsync`; null on a new entry or a `QueryFailedAsync` row) and `ClaimedOutboxEntry.ClaimToken` (required). Why: worker A's claim goes stale past `ClaimTimeout`, B re-claims (new token) and marks `Sent`; A's send then fails, and an unguarded `IncrementRetryAsync` set `Status=0, ClaimToken=NULL`, so the entry was delivered a third time. `Status = 3` also keeps a second resolution under one claim from flipping a `Sent` row back (`DbConnectionOutboxStoreShould.NotResolveARowItsOwnClaimAlreadyResolved`). On `false` the relay and the flush log `ClaimLost` (EventId 321, Warning, entry id + type; `OutboxLog.ClaimLost`, the shared `internal static partial` log class for the outbox's 321–323 events) and write nothing else for that entry, then carry on: no retry after a lost mark-sent, and no `OutboxRetriesExhausted` (320) log, counter or observation after a lost mark-failed — the relay now logs 320 only after `MarkFailedAsync` returned true. The relay throws `InvalidOperationException` (the sweep fails, logged) for a claimed entry without a token, a custom store's bug that would otherwise have every outcome refused. `OutboxOptions.Validate` refuses a `ClaimTimeout` that is not positive or is above `DurationLimits.LongestDuration` (one day; the claim's subtraction from now throws near `TimeSpan.MaxValue`). Tests: `DbConnectionOutboxStoreShould.NotResolveARowWhoseClaimMovedOn` and `PersistenceEngineTestBase.NotResolveARowWhoseClaimMovedOn` (all engines), `DbConnectionOutboxStoreShould.TakeOverAClaimOnlyOnceItIsOlderThanTheConfiguredClaimTimeout`, `OutboxRelayShould.LogALostClaim_*` / `.LogALostClaimInsteadOfExhaustion_WhenMarkingFailed` / `.RefuseAClaimedEntryWithoutItsClaimToken`, `OutboxCaptureShould.ClaimAndDeliverAsyncLogALostClaim*`, `OutboxOptionsShould.RefuseAClaimTimeoutThatIsNotPositive` / `.RefuseAClaimTimeoutAboveADay`.
- **Async scopes, entry-scoped context**: every scope in the relay (sweep, per-entry, cleanup) and the flush (flush, per-entry) is `await using var scope = scopeFactory.CreateAsyncScope();` — `IServiceScope.Dispose()` throws `InvalidOperationException` for a scoped service implementing only `IAsyncDisposable`, which landed in the per-entry `catch` after `MarkSentAsync` and released a delivered row back to `Pending` every sweep until `Failed`. **`MarkSentAsync` is the point of no return**: the per-entry scope is created in the loop body, the dispatch runs inside it (`OutboxDelivery.DispatchAsync`: local listeners from the entry scope, then transports), the outcome is written, and only then, in the per-entry `finally` (outside the `catch`), is the scope disposed by `OutboxDelivery.DisposeEntryScopeAsync`, which never throws: a failure is logged (`OutboxScopeDisposeFailed`, EventId 322, Warning, entry id + type) and never retries the entry. On the failure path the `catch` has already logged the delivery's own exception and released the entry, so the disposal cannot mask it. Nothing after a true `MarkSentAsync` reaches the `catch`: the relay's `OutboxSent` observation also moved into the `finally`, and both it and the exhausted observation go through a guard that logs an observer's throw (`OutboxObservationFailed`, EventId 323, Warning) and never retries. Tests: `OutboxRelayShould.KeepAnEntrySent_WhenItsScopeFailsToDispose` / `.LogTheListenersFailure_NotItsScopesDisposalFailure` / `.KeepAnEntrySent_WhenAnObserverFails`, `OutboxCaptureShould.ClaimAndDeliverAsyncKeepAnEntrySentWhenItsScopeFailsToDispose` / `.ClaimAndDeliverAsyncLogTheListenersFailureNotItsScopesDisposalFailure` (support: `ThrowingDisposeScopedService`, `ScopedServiceListener<TService>`). The relay restores `MessageContext` after each entry (`RestoreContext(previous)` in the per-entry `finally`, after the `catch`, which still runs under the entry's context): an entry whose payload fails to read before it restores its own context no longer runs its failure path under the previous entry's. The flush restores once after its loop (each of its entries sets its context first). Tests: `OutboxRelayShould.SurviveAnAsyncOnlyScopedService`, `OutboxCaptureShould.ClaimAndDeliverAsyncSurviveAnAsyncOnlyScopedService` (support: `AsyncOnlyScopedService`, `ScopedServiceListener<TService>`), `OutboxRelayShould.NotCarryAnEntrysContextIntoTheNextEntry`.
- **Backoff (`OutboxOptions.InitialBackoff` 5 s, `MaxBackoff` 5 min)**: `OutboxBackoff.Delay(options, failedAttempts)` is `InitialBackoff` doubled per failed attempt after the first, capped at `MaxBackoff` (doubling stops before it could overflow; a zero `InitialBackoff` is no backoff). The relay passes `Delay(options, entry.RetryCount + 1)` to `IncrementRetryAsync`; the flush passes `Delay(options, 1)` (a by-id claim only takes a never-attempted row), resolving `IOptions<OutboxOptions>` from its own scope (defaults when absent). The pending claim adds `NextAttemptAt <= @Now` (`IClaimableTableSchema.NextAttemptAtColumn`) beside the grace predicate on `CreatedAt`; a new row's `NextAttemptAt` is its `CreatedAt`, so the claim stays one predicate per column, and `NextAttemptAt` is `NOT NULL`. "Now" is the store's injected `TimeProvider` (see Time below). The by-id claim is untouched: `RetryCount = 0` already means never failed. Before this, a failed row was due on the very next sweep, so a broker restart marked everything Failed within `MaxRetries` sweeps. `OutboxOptions.Validate` refuses a negative `InitialBackoff` and a `MaxBackoff` below it or above `DurationLimits.LongestDuration` (one day; adding it to now throws near `TimeSpan.MaxValue`, `OutboxOptionsShould.RefuseAMaxBackoffAboveADay`). Tests: `OutboxRelayShould.BackOffExponentiallyAfterAFailedSend`, `.BackOffWithinTheConfiguredBounds`, `OutboxCaptureShould.ClaimAndDeliverAsyncBackOffAFailedEntryByTheInitialBackoff`, `DbConnectionOutboxStoreShould.NotClaimARowBeforeItsNextAttempt` and the same in `PersistenceEngineTestBase`.
- **Retrying failed entries (`IOutbox`, scoped, registered by `AddOutbox` in both modes)**: the user surface, mirroring `IDeadLetters` — `QueryFailedAsync(FailedOutboxFilter)` (Failed rows, oldest first by `Id`, optional exact `MessageType`, offset page token + `TotalCount`, like the DLQ) and `RetryFailedAsync(long id)` / `RetryFailedAsync(string messageType)`, which reset a `Failed` row to `Pending` with `RetryCount = 0`, `NextAttemptAt = now` and the claim cleared (`WHERE ... AND Status = 2`, so a pending or sent row is never touched); they return whether / how many rows changed. `OutboxOperations` (internal sealed; hosts inject `IOutbox`; `Conduit.Persistence.IntegrationTests` builds it through an `InternalsVisibleTo`) delegates to the same-named `IOutboxStore` members. The id is the entry's `long` key (two `string` overloads could not coexist). A retried row keeps its `MessageId` and its `CreatedAt`, and loses its `FailedAt`: should it fail again, `FailedRetention` counts from that failure. `PageSize` is checked (see validated options above). Tests: `OutboxShould`, `PersistenceEngineTestBase.RetryAFailedEntry`.
- **Capture-only (`OutboxOptions.CaptureOnly`, default `false`)**: for a process sharing its outbox table with another process whose relay owns delivery (for example a separate identity host beside the application that relays) — a second relay could claim a row whose listener lives only in the other process and mark it sent unhandled. Registers `OutboxCapture` as `IOutboundInterceptor` and `OutboxBehavior<,>` (rows still written on the caller's transaction) but **no** `OutboxRelay`, and `IOutboxFlusher` is the singleton no-op `CaptureOnlyOutboxFlusher`. Publishes with no ambient transaction are not captured and still deliver locally, as without an outbox.
- `IOutboxStore` interface with built-in `DbConnectionOutboxStore` (raw ADO.NET). Includes `ClaimByMessageIdsAsync` for the post-commit flush's entry claiming, and `QueryFailedAsync` / `RetryFailedAsync` behind `IOutbox`.

## Inbox (idempotent message processing)

- Application-level message deduplication for all inbound wire messages (commands, queries, events). Prevents duplicate handler execution when brokers redeliver messages. Duplicates are silently discarded — no result caching.
- `InboxInterceptor` — `IInboundInterceptor` gate that dedups on `MessageContext.Current.MessageId` via a **single atomic operation**: it calls `IInboxStore.RecordAsync`, which returns whether the row was newly inserted. Newly inserted → proceed (return true); already present → discard (observe `InboxDuplicate`, return false). No-op when no `MessageContext` (local dispatch). (Previously it did `ExistsAsync` then `RecordAsync` as two statements on two connections — a check-then-act TOCTOU race where two concurrent redeliveries of the same MessageId could both pass `ExistsAsync` before either recorded, running the handler twice. The atomic insert closes that window.) It remembers the id it newly recorded in `internal AdmittedMessageId` (null for no context, a duplicate, or a gate that never ran). `AddInbox` registers it as a scoped concrete `InboxInterceptor` with a forwarding `IInboundInterceptor`, so the dispatch scope's gate and its `InboxErrorInterceptor` are one instance.
- `InboxErrorInterceptor` (internal) — the `IInboundErrorInterceptor` `AddInbox` registers: a failed broker dispatch (`BrokerTransportBase.TryCaptureErrorAsync`, which offers every failure to every registered error interceptor) removes the gate's `AdmittedMessageId` via `IInboxStore.RemoveAsync`, so the broker's redelivery of an abandoned message, or a DLQ replay (which carries the original `MessageId`), runs instead of being discarded as a duplicate. (Previously the record was never released: an abandoned listener failure's redelivery was discarded and acknowledged, one transient failure losing the message with no dead-letter row, and a replay inside `RetentionPeriod` was discarded too.) Releases only what this dispatch recorded — a failure before the gate ran (the fresh capture scope of `SettleUndispatchableAsync`, a gate ahead of the inbox that threw) or a duplicate leaves another delivery's record alone, since that delivery may have succeeded. Always returns `false` (captures nothing; the DLQ and the transport decide the settlement); a `RemoveAsync` failure is caught and logged (EventId 330 `InboxReleaseFailed`, Warning). It is also the `IInboundFailureObserver` (`Conduit.Runtime`) `AddInbox` registers (`TryAddEnumerable` under both interfaces, two scoped instances sharing the scope's one gate): the HTTP `/dispatch`/`/publish` endpoints and the hub's `Dispatch`/`Publish` call `OnDispatchFailedAsync` for an `InternalError` result, an `EventListenerException` or an `EventDispatchException` (never a refusal or a gate's discard), with `CancellationToken.None`, and the same `ReleaseAsync` runs. Without it a trusting edge (`trustCallerContext: true`, `TrustCallerContext`) kept the failed attempt's record, and a Conduit retry under the same `MessageId` (the outbox relay's `StartDispatchFromTransport(entry.MessageId, ...)` on every attempt, `TransientErrors<T>()` re-running `next()` in the same context) was answered `Ok(null)` and lost (CONDUIT-80). Tests: `InboxErrorInterceptorShould`; through `FakeBrokerTransport` (`Conduit.TestUtils`), `InboxEndToEndShould.LetARedeliveryRunAfterTheFirstAttemptFailed`, `.LetADeadLetterReplayRunAfterTheFirstAttemptFailed`, `.ReleaseTheRecordOfAnEventItsTypeCannotRead`, `.KeepTheRecordOfASucceededDeliveryWhenADuplicateFailsBeforeDispatch`; over the real edges, `InboxOverHttpShould`/`InboxOverSignalRShould` (`.RunTheRetryOfAFailedTrustedDispatch`, `.RunTheRetryOfAFailedTrustedEvent`; HTTP also `.RecordNothingBehindADistrustingEdge`), which is why this test project references both edge packages.
- `IInboxStore` interface with `ExistsAsync`, `RecordAsync` (returns `Task<bool>` — `true` when the row was newly inserted, the atomic dedup primitive), `RemoveAsync` (releases a failed dispatch's record; module-owned `DELETE ... WHERE MessageId = @MessageId`, identical on all engines, a no-op for an unrecorded id), `DeleteExpiredAsync`, `EnsureTableExistsAsync`. Built-in `DbConnectionInboxStore` (raw ADO.NET) returns rows-affected > 0 from `RecordAsync`; the insert SQL is built once via `ISqlDialect.BuildInsertOrIgnoreSql` (SQLite: `INSERT OR IGNORE`; engine variants in their packages) so rows-affected is 0 on a duplicate. `ExistsAsync` remains for callers/tests but is no longer on the dedup hot path; its probe SQL comes from `ISqlDialect.BuildExistsSql` (SQL Server omits the `LIMIT 1`). Table schema: `MessageId` (PK) + `ProcessedAt`.
- `InboxCleanup` — `BackgroundService` that periodically removes expired entries.
- `InboxOptions` — `RetentionPeriod` (default 30min), `CleanupInterval` (default 5min), checked by `InboxOptions.Validate` (see validated options above).
- **Edge case: record-then-crash** — if process crashes after `RecordAsync` but before handler completes, the message is recorded as processed but was never handled (no one runs `InboxErrorInterceptor`). At-most-once semantics. Standard trade-off (MassTransit/Wolverine same behavior). Users needing at-least-once should use broker-native retry without the inbox.
- **Broker-native dedup** — ASB `RequiresDuplicateDetection`, SQS FIFO `MessageDeduplicationId` are viable alternatives. Not abstracted by Conduit — configure via passthrough broker options.

## Dead Letter Queue (capture failed inbound messages, browse, replay)

- `IDeadLetters` — user-facing API: `QueryAsync(DeadLetterFilter)`, `GetAsync(id)`, `ReplayAsync(id)` / `ReplayAsync(ids)` / `ReplayByTypeAsync(type)`, `DiscardAsync(id)` / `DiscardAsync(ids)`. Implemented by `Runtime.DeadLetterQueue.DeadLetters`.
- `IDeadLetterStore` + `DbDeadLetterStore` — database persistence (raw ADO.NET; module-owned SQL with pagination/type-names from `ISqlDialect`). Table `conduit_dead_letters`, with two nullable replay-claim columns, `ReplayClaimToken` and `ReplayClaimedAt`.
- **Capture**: `BrokerTransportBase` offers an inbound message it could not handle (after resilience retries) to every registered `IInboundErrorInterceptor`, each in its own guard (one that throws is logged, EventId 510 `ErrorInterceptorFailed`, and the rest still run): `DeadLetterErrorInterceptor` writes it to the store, and with the inbox, `InboxErrorInterceptor` releases its record. When any captured it, the transport then acknowledges it, once (a capture's acknowledgement is outside the capture's guard, so one that throws reaches the broker client instead of a second settlement). What is captured, and what happens when nothing captures it (no DLQ registered, or the store write failed): a message that fails **before dispatch** (unreadable body, scope or mediator not built — `SettleUndispatchableAsync`, through a fresh scope) and an **event this host cannot read** (`BadRequestException`/`ContractMismatchException` from the event read, `ConduitRuntime.DeserializeWireEvent`, or an unknown type) — otherwise acknowledged, since a redelivery fails the same way; an `EventListenerException` — otherwise abandoned (RabbitMQ rejects it to `{system}-dead-letter`, the other brokers redeliver); a request whose result is `InternalError` (only that code: a refusal — 404/409/412, any `ConduitException` — is the caller's answer, never captured), with `DispatchError.Reference` passed as `TryCaptureAsync`'s `reference` and stored in the entry's `Reference` column (the synthetic exception names only the answer; the reference finds the logged one) — otherwise acknowledged. Any other event refusal (the type filter's `ForbiddenException`) is acknowledged uncaptured. A `[FireAndForget]` command (no reply address; a replayed command or query arrives the same way) is settled by its `HandleWireRequestAsync` result: `InternalError` or a thrown dispatch is captured with the reference, otherwise abandoned, as a listener failure; `BadRequest`/`ContractMismatch` is captured, otherwise acknowledged; any other refusal is acknowledged uncaptured with a Warning, EventId 511 `FireAndForgetCommandRefused` (not 510, which is an error interceptor that threw) (`BrokerTransportBaseShould`, `RabbitMqDeadLetterShould.CaptureAFailedFireAndForgetCommand`). Pinned per broker by `{Transport}DeadLetterShould.CaptureAMalformedBody` / `.NotCaptureABusinessRefusal`, container-free by `BrokerTransportDeadLetterShould` (`CaptureAnEventItsTypeCannotRead`, `NotCaptureAForbiddenEvent`, `SettleACaptureOnceWhenItsAcknowledgementFails`, `AcknowledgeACapturedRequestOnce`, `OfferAFailureToEveryErrorInterceptor`, `OfferAFailureToTheOtherErrorInterceptorsWhenOneThrows`).
- **Replay is claimed, then redelivered, then removed**: `DeadLetters.ReplayAsync` reads the entry, claims it (`IDeadLetterStore.ClaimForReplayAsync`, one module-owned `UPDATE ... SET ReplayClaimToken, ReplayClaimedAt WHERE Id = @Id AND (ReplayClaimToken IS NULL OR ReplayClaimedAt <= @ClaimCutoff)`, rows affected 1 = held; the same statement on all four engines, through `ISqlDialect.BuildReadCommittedSql` so a SQL Server session carrying Snapshot waits and re-checks instead of failing with 3960), redelivers, then removes (`RemoveAsync`, by id). A claim held elsewhere returns null and the replay fails with "Dead letter entry is already being replayed, or was removed", without redelivering. A redelivery that fails releases the claim (`ReleaseReplayClaimAsync`, `WHERE Id AND ReplayClaimToken = @ClaimToken`, so a taken-over claim is left alone). Why not one statement: MySQL has no `DELETE ... RETURNING`, and remove-first would lose the message to a crash before the redelivery; claim-first is one statement everywhere and at least once. At least once: a crash (or a removal that fails, EventId 313 `DlqReplayedEntryNotRemoved`, Warning; the result is still a success, the message was re-published) leaves the entry claimed, and once the claim is older than `DbDeadLetterStore.ReplayClaimTimeout` (five minutes, a constant: a replay is one publish and a delete) the next replay takes it over and re-publishes it. A release that fails is EventId 314 `DlqReplayClaimNotReleased` (Warning); the claim then times out. (`DeadLetters` logs 311 `DlqReplaySucceeded`, 312 `DlqReplayFailed`, 313, 314: renumbered from 301-304 before the first release, which overlapped `ConduitBackgroundDispatcher`'s 300/301/303 in core, so an alert keyed on 303 caught both. The outbox is 320-323, the inbox 330.) The removal and the release run with `CancellationToken.None`: a redelivered entry is settled even when the caller has cancelled. Before this, redeliver then remove were two unguarded steps: two concurrent replays of one id both redelivered. Tests: `DeadLetterEndToEndShould.RedeliverAnEntryOnceWhenTwoReplaysRace` (`GatedRedeliveryTransport` holds the first redelivery open while a second replay runs), `DeadLettersShould.ReleaseItsClaimWhenTheRedeliveryFails` / `.RefuseToReplayAnEntryAnotherReplayHolds` / `.ReportAReplayRedeliveredWhenOnlyTheRemovalFails` (`StubDeadLetterStore` tracks claims, never times them out, and fails `RemoveAsync` on `FailRemoval`), `DbDeadLetterStoreShould.ClaimAnEntryForOneReplayAtATime` / `.ReleaseOnlyTheClaimItIsGiven` / `.TakeOverAReplayClaimOnceItIsAbandoned`, `PersistenceEngineTestBase.ClaimADeadLetterForOneReplayUnderConcurrency` (twenty claims at once, all engines).
- **Replay**: re-publishes via `IConduitTransport.RedeliverAsync(envelope, RedeliveryIds?, ct)` — `DeadLetters` passes the entry's `MessageId`/`CausationId`/`ConversationId` when all three are present (`RedeliveryIds` throws `ArgumentException` for a blank one; an entry captured outside a context has none, and gets null ids, so a fresh message id), and each broker transport maps them onto its native properties through `BrokerTransportBase.BuildRedeliveryHeaders` (no source-app stamp: stamped with the replaying host's `ApplicationName`, a replayed event would be dropped by the self-published-event filter the moment it arrived back, silently voiding the replay — so replay must not move onto the normal publish path, which stamps), targeting the inbound queue directly. HTTP/SignalR ignore the ids (they never receive a DLQ replay). Any handler instance picks it up (`{Transport}DeadLetterShould.ReplayWithTheOriginalIds`). The inbox records an id before the handler runs, and the failure that dead-lettered the message released it (`InboxErrorInterceptor`), so the replay runs inside `InboxOptions.RetentionPeriod` too — including an event its type could not read, whose id the gate recorded before the body read failed. A message that failed before dispatch never reached the gate.
- **Database-only by design (for now).** Broker-native DLQ stores (wrapping ASB/RabbitMQ/SQS/ActiveMQ native DLQs as the Conduit store) were evaluated and deliberately *not* implemented: non-uniform/fragile browse per broker, best-effort filtering, no reliable counts, racy removal, and it duplicates the DB store unevenly. Not a permanent exclusion — could be added later as an additive per-transport option. The broker's own DLQ still acts as an infrastructure safety net when Conduit's DLQ is not enabled. See [docs/dead-letter-queue.md](../../docs/dead-letter-queue.md).
