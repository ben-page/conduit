# Conduit.Transport.SignalR

- `ConduitHub` — inbound SignalR hub with `Dispatch(type, payload, context?, headers?)` and `Publish(type, payload, context?, headers?)` methods, injects `IWireMediator`, `IEnumerable<IDispatchContextEnricher>`, `IEnumerable<ConduitServerInfo>`, `IOptions<ConduitSignalROptions>` and `IServiceProvider` via constructor. `Dispatch` writes a refusal in the reader's language on the way out (`RefusalRendering.RenderResult` with the injected `IServiceProvider` and `MessageContext.Current`). Both optional params are `Dictionary<string, string>?`:
  - `context` carries `MessageContext` correlation (`MessageId`, `CausationId`, `ConversationId`) for cross-service propagation — browser clients pass `null`, C# clients (`SignalRTransport.BuildContext`) populate it. It is read only when `ConduitSignalROptions.TrustCallerContext` is true, and then honored only when `MessageId` and `ConversationId` are both present and every supplied id passes `MessageContextIds.IsValid` (an empty `CausationId` is absent); `ReadCallerIds` discards the set on one bad id. Otherwise the server's ids are used: fresh self-causating ones when `properties` exist, else no context (the mediator mints). Pinned by `ConduitHubShould.IgnoreCallerContextUnlessConfigured`/`HonorCallerContextWhenConfigured`/`MintFreshIdsForACallerContextThatIsNotPlainTokensEvenWhenConfigured` (CR/LF reaches the hub intact over JSON).
  - `headers` carries caller-supplied values (e.g. tenant code). `StartMessageContext` seeds the property bag from `headers`, then runs registered enrichers via `DispatchContextEnrichment.Apply(enrichers, Context.User, ...)` — enrichers run **last** so server-trusted values (e.g. authenticated user id) overwrite any spoofable client header. The merged bag flows into `MessageContext.Properties` via `StartDispatchFromTransport(messageId, causationId, conversationId, properties)`, reaching pipeline behaviors. When `properties` exist but no trusted correlation is supplied, fresh IDs are minted so the properties still reach the generated mediator.
- `SignalRTransport` — outbound dual-mode transport with lazy connect (`EnsureConnectedAsync`). `UseSignalR(hubUri?, configure?)` binds `SignalROptions` from the endpoint's configuration section (`builder.Configuration?.Bind(options)`), applies the `hubUri` argument and then the `configure` callback if given, registers **both** the bound `SignalROptions` and the `SignalRTransport` as keyed singletons by endpoint name (matching the broker transports' pattern — the options are inspectable, not bound and dropped), and calls `UseTransport<SignalRTransport>()`. It replaced the old `UseSignalR(EndpointBuilder, Uri)` rather than overloading it: source-compatible (`UseSignalR(hubUri)` still binds) but **binary** breaking, since the signature gained parameters. A null hub URI now surfaces as an `InvalidOperationException` from the post-merge validation naming both ways to supply it, not an `ArgumentNullException` from a guard clause. Client mode sends `MessageContext.Current` correlation as the `context` dictionary (built by `BuildContext()`). It always invokes the hub with **all four args** — `Dispatch`/`Publish`/`RedeliverAsync` pass `noHeaders = null` for the `headers` arg because SignalR rejects arity mismatches on the wire (the outbound transport does not forward headers itself).
- `AddConduitSignalR(configure?)` registers SignalR services and server-mode transport as non-keyed `IConduitTransport` (for event broadcast to connected clients), plus `IOptions<ConduitSignalROptions>` (`AddOptions` + `Configure(configure)` when given, so callbacks from several calls all apply). `ConduitSignalROptions` (sealed, one property `TrustCallerContext`, default false) is the inbound hub's options, distinct from the client-mode `SignalROptions`. `AddConduitSignalR(serverInfo, configure?)` kept both overloads: it adds the `ConduitServerInfo` singleton and forwards `configure` (`SignalRConfigurationShould.LeaveTheHubDistrustingCallerContextUnlessARegistrationConfiguresIt`). `AddConduitSignalR(null)` is ambiguous between them (CS0121); a typed null variable is not.
- **Dual-mode SignalRTransport**: Server mode (IHubContext, pushes events) and client mode (HubConnection, sends commands + receives events). Client mode uses lazy connect (auto-starts on first use via `EnsureConnectedAsync`).
- **Configuration keys** (`Conduit:Endpoints:{endpointName}`, bound before the `configure` callback runs): `HubUri` (required). See [`docs/configuration-reference.md`](../../docs/configuration-reference.md#loading-from-iconfiguration) and [`docs/transports/signalr.md`](../../docs/transports/signalr.md#client-mode-service-to-service).
