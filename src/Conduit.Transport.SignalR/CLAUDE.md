# Conduit.Transport.SignalR

- `ConduitHub` — inbound SignalR hub with `Dispatch(type, payload, context?, headers?)` and `Publish(type, payload, context?, headers?)` methods, injects `IWireMediator`, `IEnumerable<IDispatchContextEnricher>`, `IEnumerable<ConduitServerInfo>`, `IOptions<ConduitSignalROptions>`, `IServiceProvider` and `ILogger<ConduitHub>` via constructor. `Dispatch` writes a refusal in the reader's language on the way out (`RefusalRendering.RenderResult` with the injected `IServiceProvider` and `MessageContext.Current`). `Publish` catches the `ConduitException` `HandleWireEventAsync` rethrows for a refused event and throws `HubException` with the rendered message (`TypeFilterShould.RefuseAnUnlistedEventAndAnswerTheCaller`); an `EventDispatchException` (a failure outside the listeners, already logged with its reference) throws `HubException` with the rendered message of `ConduitRuntime.UnexpectedFailure(reference)`, the fixed "An unexpected error occurred." and nothing of the exception (`ConduitHubShould.FailAPublishWhoseBehaviorThrowsWithTheFixedMessage`); a listener's `EventListenerException` throws the same `HubException`, from `ConduitRuntime.UnexpectedEventFailure(logger, type, failure)`, which mints the reference at the edge and logs `PublishError` with the first listener failure on the injected `ILogger<ConduitHub>` (`ConduitHubShould.PropagateListenerFailureAsHubError`). Left to SignalR it was a generic invocation error with no logged reference, and with `EnableDetailedErrors` the listener's message. `Dispatch` (an `InternalError` result) and `Publish` (the `EventListenerException`/`EventDispatchException` arms) report every unexpected failure to each `IInboundFailureObserver` from the injected (invocation-scoped) `IServiceProvider` through private `ReportFailureAsync` before answering (the inbox releases its record, CONDUIT-80); a throwing observer is logged Warning EventId 101 `FailureObserverFailed` (100 is `SignalRTransport`'s) (`InboundFailureObserverShould`). Both optional params are `Dictionary<string, string>?`:
  - `context` carries `MessageContext` correlation (`MessageId`, `CausationId`, `ConversationId`) for cross-service propagation — browser clients pass `null`, C# clients (`SignalRTransport.BuildContext`) populate it. It is read only when `ConduitSignalROptions.TrustCallerContext` is true, and then honored only when `MessageId` and `ConversationId` are both present and every supplied id passes `MessageContextIds.IsValid` (an empty `CausationId` is absent); `ReadCallerIds` discards the set on one bad id. Otherwise the server's ids are used: fresh self-causating ones when `properties` exist, else no context (the mediator mints). Pinned by `ConduitHubShould.IgnoreCallerContextUnlessConfigured`/`HonorCallerContextWhenConfigured`/`MintFreshIdsForACallerContextThatIsNotPlainTokensEvenWhenConfigured` (CR/LF reaches the hub intact over JSON).
  - `headers` carries caller-supplied values (e.g. tenant code). `StartMessageContext` seeds the property bag from `headers` (`ToProperties`: an `OrdinalIgnoreCase` dictionary — property names are case-insensitive at every edge, `DispatchEnricherShould.ReadAHeaderNameRegardlessOfCase`), then runs registered enrichers via `DispatchContextEnrichment.Apply(enrichers, Context.User, ...)` — enrichers run **last** so server-trusted values (e.g. authenticated user id) overwrite any spoofable client header. The merged bag flows into `MessageContext.Properties` via `StartDispatchFromTransport(messageId, causationId, conversationId, properties)`, reaching pipeline behaviors. When `properties` exist but no trusted correlation is supplied, fresh IDs are minted so the properties still reach the generated mediator.
- `SignalRTransport` — outbound dual-mode transport with lazy connect (`EnsureConnectedAsync`). `UseSignalR(hubUri?, configure?)` binds `SignalROptions` from the endpoint's configuration section (`builder.Configuration?.Bind(options)`), applies the `hubUri` argument and then the `configure` callback if given, registers **both** the bound `SignalROptions` and the `SignalRTransport` as keyed singletons by endpoint name (matching the broker transports' pattern — the options are inspectable, not bound and dropped), and calls `UseTransport<SignalRTransport>()`. The transport is registered through a **keyed factory** (`AddKeyedSingleton(name, (serviceProvider, _) => new SignalRTransport(BuildHubConnection(uri, configureConnection), serviceProvider.GetService<ConduitTypeRegistry>()))`), never an instance: the container disposes a factory-built singleton and never an instance registration, so the `HubConnection` used to outlive the host (`SignalRTransportShould.BeDisposedWithTheContainer`). `DisposeAsync` is idempotent, because the container disposes the instance once per registration that resolved it (the keyed `SignalRTransport` and the keyed `IConduitTransport` forwarder); a send after disposal throws `ObjectDisposedException`. `SignalROptions.ConfigureConnection` (`Action<HttpConnectionOptions>?`, code only — the binder never touches a delegate without a matching key) is passed to `WithUrl(hubUri, …)`, so a hub behind `RequireAuthorization` is reachable (`UseSignalRShould.PassConnectionOptionsThrough`: an `AccessTokenProvider` reaches the negotiate request as `Authorization: Bearer`). It replaced the old `UseSignalR(ConduitEndpointBuilder, Uri)` rather than overloading it: source-compatible (`UseSignalR(hubUri)` still binds) but **binary** breaking, since the signature gained parameters. A null hub URI now surfaces as an `InvalidOperationException` from the post-merge validation naming both ways to supply it, not an `ArgumentNullException` from a guard clause. Client mode sends `MessageContext.Current` correlation as the `context` dictionary (built by `BuildContext()`), only when all three ids pass `MessageContextIds.IsValid`, else `null` (`SignalRTransportShould.NotForwardAContextThatIsNotPlainTokens` in `Integration/SignalRTransportIntegrationShould.cs`, against `Support/ContextRecordingHub`, which records the raw argument). It always invokes the hub with **all four args** — `Dispatch`/`Publish`/`RedeliverAsync` pass `noHeaders = null` for the `headers` arg because SignalR rejects arity mismatches on the wire (the outbound transport does not forward headers itself).
- **Server-mode push scope** (`SignalRTransport.SendEventAsync` → `PushAsync`): the recipients come from `ResolveRecipientsAsync` — with no `IEventRecipientResolver`, `EventRecipients.All` when `ConduitTypeRegistry.ClientVisibleEventTypeNames` contains the envelope's type, else `None`; with one, its answer for every event (`[ClientVisible]` or not). `All` → `Clients.All`, `Users(ids)` → `Clients.Users`, `Groups(names)` → `Clients.Groups`, `None` or an empty list → no send. The resolver gets the event deserialized as its registry type (`eventTypesByName`, a `FrozenDictionary` over `typeRegistry.EventTypes` built only when a resolver is present) with `ConduitRuntime.JsonOptions`, or the raw `JsonElement` for a name the registry does not list. A resolver exception, a deserialize failure or a null payload is caught in `ResolveRecipientsAsync`, logged Warning with the exception (EventId 100 `RecipientResolutionFailed`, the package's first; transports number theirs from 100) and answered `None`: the transport never throws for a resolver fault, because the outbox delivers through `TransportDispatcher.BroadcastAsync`, which does not isolate transports, so a throw stopped the transports after SignalR, failed the outbox entry and resent it to those that already took it (`EventBroadcastShould.LogAndSkipTheEventWhenTheResolverThrows`, driven through `TransportDispatcher.SendAsync` with a `RecordingTransport` registered after SignalR). An `OperationCanceledException` with the send's token cancelled still propagates. Previously the transport sent every non-`[LocalOnly]` event to `Clients.All`, signed in or not (`EventBroadcastShould.PushOnlyClientVisibleEventsByDefault`, `.AskTheResolverWhenOneIsRegistered`: users via `Support/QueryStringUserIdProvider`, a group via `IHubContext.Groups`; both wait for the `ConduitServerInfo` greeting before publishing, because `StartAsync` returns at the handshake, before the server registers the connection for `Clients.All`/users/groups). `EventRecipients` is a `readonly record struct` whose `default` is `None`; `Kind`/`Names` are internal, equality is by kind and ordinal name sequence (the names are copied on construction; a null/empty name throws), `ToString` reads `Users(a, b)`. The server-mode constructor is `(IHubContext<ConduitHub>, ConduitTypeRegistry, ILogger<SignalRTransport>, IEventRecipientResolver? = null)` — the registry is required, since the default needs it, and the logger, since a resolver fault is only logged.
- `AddConduitSignalR(configure?)` registers SignalR services and server-mode transport (through a factory: `IHubContext<ConduitHub>`, the required `ConduitTypeRegistry`, `ILogger<SignalRTransport>`, and `GetService<IEventRecipientResolver>()` resolved once from the root) as non-keyed `IConduitTransport` (for event broadcast to connected clients), plus `IOptions<ConduitSignalROptions>` (`AddOptions` + `Configure(configure)` when given, so callbacks from several calls all apply). Idempotent: the options/`Configure` run on every call, then the call returns early when a non-keyed `SignalRTransport` descriptor exists (client-mode transports are keyed, so they never match), so `AddSignalR`/`AddJsonProtocol` and the transport plus its non-keyed `IConduitTransport` forwarder are added once. A second forwarder had the generated publish broadcast every event to the hub twice (CONDUIT-87; `SignalRConfigurationShould.RegisterTheServerTransportOnceWhenCalledTwice`, `EventBroadcastShould.PushAnEventOnceWhenAddConduitSignalRIsCalledTwice`). `ConduitHub` is `sealed`: a subclass is a different hub to `IHubContext<ConduitHub>` and never received push. `ConduitSignalROptions` (sealed, one property `TrustCallerContext`, default false) is the inbound hub's options, distinct from the client-mode `SignalROptions`. `AddConduitSignalR(serverInfo, configure?)` kept both overloads: it adds the `ConduitServerInfo` singleton and forwards `configure` (`SignalRConfigurationShould.LeaveTheHubDistrustingCallerContextUnlessARegistrationConfiguresIt`). `AddConduitSignalR(null)` is ambiguous between them (CS0121); a typed null variable is not.
- **Dual-mode SignalRTransport**: Server mode (IHubContext, pushes events, scoped as above) and client mode (HubConnection). **Client mode is send-only**: it registers no `On` handlers, so it does not receive the hub's events (receiving is deferred; the docs say so). Client mode uses lazy connect: `EnsureConnectedAsync` returns at once when `State == Connected`, else under the connect lock calls `StartAsync` when `State == Disconnected` — on first use and again after the connection closed for good (automatic reconnect gave up, the hub aborted it); `Connecting`/`Reconnecting` are left to SignalR, so a send mid-reconnect fails as SignalR fails it rather than racing a second start. No `connected` flag: it was set once and every send after a final close threw "InvokeCoreAsync method cannot be called if the connection is not active" until restart (`SignalRTransportShould.ReconnectAfterTheConnectionClosedForGood`, against `Support/ClosingHub`, whose `Dispatch` of `"Close"` calls `Context.Abort()`, over a connection with `WithAutomaticReconnect([])`).
- **Client-mode reply-less sends** (`SendEventAsync`, `RedeliverAsync` → `SendWithoutReplyAsync`): an event (`ConduitTypeRegistry.EventTypeNames`, the registry `UseSignalR` resolves from DI) is invoked on the hub's `Publish`; anything else — a routed `[FireAndForget]` command, the only non-event that reaches `SendEventAsync` — on its `Dispatch`, the `DispatchResult` discarded but `UnwrapReply`'d, so a refusal throws (and a failed DLQ replay is no longer reported as delivered). Without a registry (a hand-built transport) every such send is a command. `RedeliverAsync` ignores its `RedeliveryIds` argument (only broker transports capture dead letters). Previously `SendEventAsync` always invoked `Publish`, whose event switch refused a command as "Unknown message type" (`SignalRTransportShould.DispatchAFireAndForgetCommandThroughTheHubsDispatchMethod`, `.PublishAnEventThroughTheHubsPublishMethod`). Client-mode transports are keyed only, so the generated publish's broadcast loop never reaches them.
- **Configuration keys** (`Conduit:Endpoints:{endpointName}`, bound before the `configure` callback runs): `HubUri` (required).
